# 2026.306.0142 — fix(ci): the sweep runs in a workspace it owns, not the runner's (#264)

## Summary

**The required `validate / validate` check failed before it reviewed anything** — on two
independent heads, at the same step, with the same message:

```
step "Sweep the tree for withdrawn identifiers"
go: ../go.work requires go >= 1.26.8 (running go 1.26.0; GOTOOLCHAIN=local)
##[error]Process completed with exit code 1.
```

- `opencharly/charly#1099` — run `41354275367`, job `124990877965`, head `4afa3547`
- `opencharly/charly#1100` — run `41356369597`, job `124997169458`, head `a9fc2bb7`
- re-measured this round on `opencharly/charly#1102` — run `41370344019`, job `125039622862`, head `d0dd4fc2`

**Mechanism.** `go run` walks UP from `contract/` looking for a `go.work`. The directory
above it is the runner's workspace root, which **`actions/checkout` never cleans** — it
cleans only the directory it manages. A sibling job that checked out at that root leaves
its own committed `go.work` there (`opencharly/charly`'s CI uses a plain
`actions/checkout@v5` with no `path:`, and that repository tracks a `go.work`). A later job
that checks out into `repo/` inherits that residue, and the sweep dies on toolchain
resolution instead of judging the tree.

**Missed control.** The arm assumed Go would resolve the contract's own modules; nothing
made the module boundary explicit, so an ambient file the gate does not own could decide
the verdict. Nothing ties "the Go I run" to "the module I pinned".

**Blast radius.** Every PR in every repository the org ruleset covers, whenever it lands on
a runner that served a root-level checkout before it. The failure is indistinguishable
from a real finding, so authors spend a round chasing a phantom — and it blocked **four**
otherwise-green PRs this round: `charly#1099`, `#1100`, `#1101`, `#1102`, each measured at
this step (`124990877965`, `124997169458`, `125021297186`, `125039622862`).

**Deliberately NOT counted in that blast radius.** `layer-krun#2` and `layer-criu#2` also
show a red `validate / validate`, but their failure step is **`Enable auto-merge`**, which
is the repositories' `allow_auto_merge=false` setting — an operator-owned repo PATCH, not
this defect. Measured on jobs `120099882198` and `120093148970` before writing this line,
because assuming the two were the same would have overstated the fix's reach.

**Root fix.** The contract ships its own `go.mod`, so workspace mode is turned OFF for
the sweep: `GOWORK=off go run ./retired/cmd/retired-sweep …`. That is not a suppression —
it declares the module boundary the arm already intended, and it is the **same guard this
file applies two other places**, to charly's `tools/*` modules in the lint job. The fix
lives in the one org-owned file; there are no per-repo copies to update (R2).

**Diff, every item accounted for:**

| File | Change |
|---|---|
| `.github/workflows/pr-validator.yml` | the sweep step's `run:` text gains `GOWORK=off`, with the RCA and the #264 citation recorded in the comment beside the other rationale for how this step is pinned |
| `scripts/retired-sweep-arm_test.sh` | the coverage gains **case 6** (a workspace whose root carries a foreign `go.work` must still PASS) and **negative control 5** (remove the guard from a workflow copy → the coverage must go RED for that exact reason); `WS` is now a variable so a second workspace can be built, and `run_sweep` pins `GOTOOLCHAIN=local`, which is what `actions/setup-go` sets in the real job, so the case decides what the ARM does and not what a toolchain download did |

**It fails without the change, and that is asserted, not claimed.** Case 6 builds a
workspace root carrying `go 1.999.0` (a version no toolchain can satisfy) and requires the
sweep to still PASS. Negative control 5 re-runs the whole coverage against a copy of the
workflow with `GOWORK=off` removed, and **the run fails** — so if the guard were deleted,
this coverage would go red instead of silently passing. The control greps for case 6's own
failure text, so it cannot pass for the wrong reason.

