# 2026.327.1322 — fix(arm): a non-green head is reported, never completed as a failed check run

## Summary

`validate / arm` could deadlock a pull request permanently, and the only visible remedy from inside a session was an empty push — which R3 forbids. Closes **opencharly/.github#313**.

Measured on `opencharly/gst-wayland-display#12`, head `7071384`: the ruleset's three required checks (`cargo fmt`, `harness (lint · build · unit)`, `validate / validate`) all SUCCESS, the verdict a PASS, and the only red run on the head `validate / arm` itself — which then failed with `GitHub still reports the pull request as unstable after 180s`. A re-run of the failed job reproduced it (3m8s), because by then the first arm failure was itself a failing check run on the head.

The mechanism: GitHub computes `mergeable_state` over **every** check run on the head. One COMPLETED FAILURE of this **non-required** check run leaves the PR `unstable`; `enablePullRequestAutoMerge` is refused while unstable; and the job that must clear it has to complete in order to fail. The gate poisoned the condition it waits on — the POISON class `scripts/check-stalled-automerge.sh` shape 3 already documents for the REQUIRED context, one level down.

The fix is three parts, and all three are asserted:

1. **`Head check-runs` carries `continue-on-error: true`.** Its non-green classes (1 NOT-PASSED, 2 IN-FLIGHT, 3 UNREAD, 4 EMPTY) no longer complete as a FAILED check run. The **exit codes and the annotations are unchanged**, so the class table, the titles and the remedies the step prints stay exactly as they were; the step additionally writes `green=true|false` and `class=<n>` to `$GITHUB_OUTPUT`.
2. **`Enable auto-merge` is gated on `green == 'true'`** — `continue-on-error` alone would let a class 1–4 head reach the mutation — and carries `continue-on-error: true` itself, so an arming failure (head moved, auth, a persistent `unstable`) is reported rather than poisoning the head.
3. **A new `Report an unarmed head` step** runs when either did not succeed and updates ONE marker-keyed comment with the class and its remedy. A check run that is green by design can no longer be the alarm, so the comment is; marker-keying keeps a retried job from spamming the PR.

The required `validate / validate` verdict check is untouched: a BLOCK still fails it, and it is still the merge gate. What changes is that the arm job — a convenience that arms the merge the verdict already authorised — stops being able to veto it permanently.

**RCA of a failure this change itself produced (R1), already fixed in the tree:** the first run of the updated step failed case (A) with `step.sh: line 169: : No such file or directory`. Mechanism: the step now writes `$GITHUB_OUTPUT`, and the harness — like the pre-change step — never exported one; on a runner GitHub always sets it, in the harness nothing did. Missed control: the harness must mirror the runner's environment for every variable the shipped text reads, not only the ones it read yesterday. Fix: the harness exports a per-case `GITHUB_OUTPUT` (and `expect_class` reads it), which is what makes the class assertions possible at all.

Live proof of the deadlock itself is on `opencharly/gst-wayland-display#12` (the measurement quoted above). Live proof of the FIX is that PR's arm job after this merges: its head still carries the failed `validate / arm` run from before, so the first attempt there may still be refused — the honest expectation is that a **new head** (or a re-run creating a fresh job) arms, and that no future head can reach this state.
