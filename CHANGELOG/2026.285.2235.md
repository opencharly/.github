# 2026.285.2235 — fix(validator): an unresolvable engine pin names itself instead of dying silently (charly#723)

## Summary

A charly **TAG can exist with no published release** — measured live 2026-10-13: **717 tags, 272 releases** — and `vars.CHARLY_VERSION` names the *tag*. The `Ensure charly` step then `curl -fsSL`s `releases/download/$TAG/...`, 404s, and **the step died there**: every later step was `skipped`, so the run ended with **no verdict and no comment at all** (measured on `opencharly/sdk#317`) — an author could see nothing to act on. The only loud branch on that step was the *unset* pin.

**The gate now names the class instead of dying, and never reviews with a different engine.**

- `Ensure charly` classifies the failure and hands it to the gate's **existing** INCONCLUSIVE machinery: it writes `engine_unresolved`/`pin_tag`/`pin_from`/`pin_class` and exits 0; `Run the review engine` is skipped (reviewing without the pinned binary — or worse, with a stale on-PATH engine — is the exact class the pin exists to prevent); `Parse verdict` carries `INCONCLUSIVE` + **`infra`**; and the gate posts the canonical `## validator INCONCLUSIVE` comment naming the pin, the tag, the measured class and the two operator remedies.
- Being `infra`, it is **excluded from `AI_REVIEW_AUTO_CLOSE_AFTER`** — the operator's environment, not the author's diff (the split `opencharly/.github#170` established). The required check still goes **RED**, so unreviewed code still cannot merge.
- The sub-case is named with the **API**, not the release page — and that is a defect I found in my own first version by executing it live: the **page answers 200 for an existing tag whose release is absent** (it falls back to the tag view) and 404 only for a tag that does not exist; the API discriminates exactly (200 published / 404 absent / 404 nonsense), and this job holds `contents: write`, so a DRAFT shows as `draft=true`.
- A new optional **`charly-version`** input lets a specific pin — including this path — be exercised on demand without touching the org variable.
- New committed harness **`scripts/proof-unresolvable-pin.sh`** executes the changed branches against the real endpoints in the unresolvable-pin state. That is the only live way to drive this path: a dispatch would post an INCONCLUSIVE comment **and a red required check on whatever real PR it targeted**.

**Two asks of `charly#723` are deliberately NOT implemented, and the reason is measurement:**

- **Ask 3 — "make `tag-on-merge` publish a release for every tag" — is REFUTED.** The two releases that issue's thread called `draft=true` are **both published now** (`v2026.279.0513` published 2026-10-06, `v2026.250.1014` 2026-09-07); all **12 newest tags** have releases; the 445 unpublished ones are **historical**, minted before the publisher existed, and the pin only moves forward. The publisher (`charly`'s `release-binary.yml`, fired by the tag push / `workflow_run` of `tag-on-merge` / dispatch, walking tags newest-first for the newest *unreleased* one) works. Backfilling 445 releases would be churn with no consumer — and the issue's own reproduction tag `v2026.271.0720` **now resolves** (HTTP 200).
- **Ask 1 — the source-build fallback — is not added.** This step is tokenless-`curl`-only **by design** (its own comment records the token-injection failures), and a `go build` would add a Go toolchain + module-proxy dependency to the org's most sensitive file, for a state the loud comment already makes actionable for the one actor who can fix it (the operator). If the operator wants the build, it is a small addition inside the same branch — say so and it goes in.

Driver: `opencharly/charly#723` (the issue lives in the *pin's* repo, the fix in the *gate's*; it is closed from that thread once this lands).
