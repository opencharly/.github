# 2026.269.1441 — feat(ci)!: re-validate the PR on a body edit (edited trigger), org-wide

## Summary

Add `edited` to the ONE org-wide required PR-validator workflow, so a PR
title/body edit re-runs the gate — eliminating the empty "docs: re-freeze …"
commits authors push solely to re-trigger it.

### RCA (8-step, R1)

**Unexpected.** To correct a PR body after opening/last push, authors were
forced to push an **empty commit** (`git commit --allow-empty -m "docs: re-freeze
the PR body against the final head"`) just to fire a new workflow event.

**Mechanism.** `org-wide-pr-validator-required.yml` fired on
`pull_request: types: [opened, synchronize, reopened, ready_for_review]` —
**`edited` was absent**. A body-only edit therefore started no run, so the
validator never re-read the corrected body; the only way to get a new run was a
NEW commit.

**Root cause.** The trigger list treated the PR **body** as immutable after the
event, when the body is a first-class gate input (body-truthfulness, the body IS
the changelog, the attribution footer). The correct model: the validator
validates the PR (diff + body); a body change is a PR change and must re-run it.

**Blast radius.** Every repo in the org (the org ruleset points them all at this
one file).

### Fix

`types: [opened, synchronize, reopened, ready_for_review, edited]`.

**Loop-safe.** Nothing in the org edits a PR body/title — the validator only
posts issue comments and runs `gh pr update-branch` (which fire `issue_comment`
and `synchronize`, never `edited`) — so the new trigger cannot self-trigger.

**POISON remedy (documented in-file).** Two runs on one head produce two
same-name `validate / validate` check runs; branch protection requires ALL of
them to pass, so a completed prior FAILURE can keep a green re-run BLOCKED. The
remedy is `gh run rerun <run-id>` on the failed run:
- **Docs:** GitHub "Re-running workflows and jobs" — a re-run reuses the SAME
  `GITHUB_SHA`/`GITHUB_REF`.
- **Measured live** on opencharly/sdk#301: the head carried exactly ONE
  `validate / validate` check run BEFORE the re-run (`completed failure`) and
  exactly ONE AFTER (`in_progress`, new id) — **no duplicate minted**. This is
  `actions: write`-free and needs **no new SHA**, so it keeps the gate
  capability-free (no `checks: write`), honoring the org's T4 decision
  (`CHANGELOG/2026.251.0758.md`: no capability escalation / no self-modifying
  guardrail behavior on this workflow).
