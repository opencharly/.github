# 2026.305.2033 — feat(gate)!: the org-wide sweep for a withdrawn name becomes a merge gate

## Summary

The org's reach for a **withdrawn name** is prose. The contract that owns those names now publishes them — and a sweep that finds them — and this PR adds the **arm**: the sweep, run over every repository the org's gate already covers, as a **STEP of the required `validate` job**.

The producer side is landed and tagged: `opencharly/spec#289` merged as `547fcc4155f25c2995b390ca76c9b80288b27483`, tagged **`v0.2026305.1919`**. It carries `retired/identifiers.json` (the canonical list of the 11 withdrawn names, with each name's surface kind, scope, replacement and reason) and `retired/cmd/retired-sweep` (the sweep, and the rule that classifies a hit). This PR is the **consumer** side: the arm that runs it, org-wide, on every pull request — and, in round 2, the assertion that the org's **own rulebook** is what is doing the reviewing.

**Why a STEP and not a job of its own.** The org's ONE required context is `validate / validate` — the `validate` job — and GitHub reports a **SKIPPED** job to the merge gate as a **SUCCESS**. A sweep in a job of its own, with the review job declared `needs: sweep`, would therefore be **DEFEATABLE**: the sweep fails, the review is skipped, the required check reports success, and the pull request merges. A step that **fails** the required job cannot be defeated that way — the required context goes red and the merge gate stops. So the arm is a merge gate from its first run, with **no ruleset change and no operator step** between the merge and the gate.

**What the arm reads, and what it holds:**

| input | where it comes from | why |
|---|---|---|
| the tree under judgement | the PR's **head**, checked out from the base repository | the head's SHA exists in the base repo only for a same-repository PR; the same guard the org-wide caller carries makes the arm **inert for a fork**, not broken |
| the **contract** at a pinned tag (`v0.2026305.1919`) | a plain, **unauthenticated** clone | the names and the sweep are the CONTRACT's — this repo holds **no second copy** of the rules, and the pin moves only through a PR here |
| the org's **records table** | `scripts/retired-records.json` in this repo | every mention of a withdrawn name that is **not** a carrier — history, a denial, an explanation — classified **BY HAND**, each entry with its reason |

A record that covers **no** hit is itself a finding, so the table is a live classification and not a list of excuses: a stale record reddens the arm exactly like a carrier does.

**The org-wide reach, MEASURED — not claimed.** Every repository the org's ruleset targets (active, non-fork, `main`-default: **416 repos**), each refreshed to its current tip, swept with the binary built from the pinned tag and the table as committed here: **8220 files read** (1579 Go, 6641 text), **10 hits in 6 repositories, all 10 covered by the table**, **0 carriers**, **0 stale records**, and **416/416 exits 0**. The org carries **no live use of a withdrawn name** today, so the arm is a gate from day one and not a gate that starts red. (Numbers and the per-repo verdicts are in block 2.) The measurement was taken at round 1's head and **re-run at this head's tips** with identical results (block 2c), because round 2 changes **nothing the sweep reads** — the arm's step text, the pinned tag and the table are byte-identical between the two commits, which is checked in block 2c — and the sweep was also re-run against **this** repository's real tree at the final head (block 2b).

### Round 1's BLOCK — the RCA, with the missed control

Round 1's review returned **BLOCK** on four findings. Each is fixed or answered below, and the fix of the first one uncovered a defect that is **bigger than this PR**.

**Finding 1 — the T4 sign-off the body asserted was not on the thread.** *Mechanism:* the body's T4 paragraph was written as a statement of the plan ("is posted on the thread … at the operator's explicit direction") while the comment did not yet exist, and the commit was pushed before the comment was posted — the paragraph was true of the intended order and false of the state at review time (the thread was empty). *Missed control:* the pre-push gate is this repo's own `workflow-checks` job plus the two body gates (`pr_body_lint.py`, `check-pr-body-diff.mjs`), and **all three read the repo**; none of them can read the PR's **comment thread**, so nothing in the local gate can tell that a sentence about the thread is untrue. The rule's gate lives in the thread, the gate that checks the body lives in the repo — that gap is the missed control, and it is general: any PR here whose body makes a claim about a comment, a sign-off, or a prior review round. *Root fix:* the order is inverted — the sign-off is posted **first**, then the body is written to match the thread, then the commit is pushed **once**; the body's T4 paragraph now describes the **state**, not the plan.

**The defect underneath finding 1 — the org rulebook was NOT in force.** The reviewer's line *"with no designated maintainers configured"* is **not** the org rulebook's clause — it is the **engine's generic prompt's** clause. That is the tell, and it is the serious finding of this round. *Mechanism:* the org variable `AI_REVIEW_PROMPT` had its **visibility narrowed to `private`** on 2026-10-22 (`updated_at` 2026-10-22T00:08:14Z, `selected_repositories_url: null`). GitHub exposes a `private` organization variable only to **private or internal** repositories, and every repository the gate covers is **public** — so `vars.AI_REVIEW_PROMPT` resolved **empty** everywhere, and the engine's `envStr("AI_REVIEW_PROMPT", embeddedPrompt)` **silently fell back** to its embedded generic prompt (2857 bytes) instead of the org's rulebook (35574 bytes on disk, 35301 characters). The fallback still returns a plausible PASS/BLOCK, so **no check reddened**: the org's own rulebook — T1–T13, the maintainer-account model, the R1–R10 accounting — was not judging the org's PRs from 2026-10-22 until now. *Evidence:* the round-1 validator job's own environment dump at the moment it ran — `AI_REVIEW_PROMPT:` **empty**, while `AI_REVIEW_MAINTAINER: atrawog,aitrawog` was present (`job-validate.log:420`); the engine's debug `system=2857` against the rulebook's 35574; an A/B across three real runs (2026-09-22 public `system=28604`; 2026-10-14 populated `system=35327`; 2026-10-30 public `system=2857`); and the variable was the **lone outlier** among the org's 24 — the other 23 were `visibility: all` — while the org has exactly **one** private repository, so the narrowing could never have had an intended effect. *Missed control:* nothing asserted that the org rulebook reached the reviewer, and no check compared the prompt the engine assembled against the org's, so the reviewer's remark read as a policy fact instead of a symptom. The missing control is a **precondition on the review itself*: the required job must be able to *tell* that it is judging under the org's rulebook, and fail when it is not. *Root fix, in the control as well as in the code:* (1) the operator configuration — the variable's visibility is restored to `all`, and its **value is untouched**, byte-identical, `sha256 8c41a8ef…f539` before and after; (2) the product — the `validate` job now **asserts the org rulebook is in force** before it reviews anything: empty → exit 1 naming the cause (`VISIBILITY`), a prompt that names no project → exit 1, because the engine's generic fallback names none; (3) the coverage — `scripts/assert-org-rulebook_test.sh`, 3 discriminating cases + 3 negative controls, running the **shipped step text**; (4) the documentation — `AGENTS.md` now states that the variable's **visibility is load-bearing** and that the assert exists to make the drift loud.

**Finding 2 — "offline" mislabelled a network-dependent test.** *Mechanism:* the CI step's label said "offline" because the step's *text* is extracted and run locally, but the test clones the contract from GitHub and `go run`s it — the label described the extraction, not the network. *Missed control:* the harness job's step names were never checked against what the scripts do; this repo's gates test the scripts, not the labels that describe them. *Root fix:* the step is labelled for what it does — *"network: the pinned contract is cloned; the step text is extracted"* — and **quoted**, because an unquoted value containing `": "` is a YAML break (my own gate caught that one); the test's header says the same and offers `--contract <dir>` for a pre-provisioned checkout; the body's counts now name the split: of the job's **14** `run:` steps, **13 are offline and 1 is networked**.

**Finding 3 — the setup-go count.** *Mechanism:* the count was written when the diff had one new site; the arm's own site in `pr-validator.yml` came later, making it two, and "a fourth `actions/setup-go` site" reads as *one added site* rather than *the third and fourth in the repository*. *Missed control:* no gate cross-checks the body's prose numerals against the diff — the two body gates check the file table and the structure, not every count in the prose; the counts have to be **derived from the diff** at authoring time and named with their unit. *Root fix:* this diff adds **two** `actions/setup-go` sites — the **third and fourth** in this repository — and both are *uses* of the ref `scripts/action-runtime-pins.tsv` already declares (no new pin row, no pin left unused; the runtime checker is green at 5 audited pins).

**Finding 4 — the workspace-clean question (a verification request, not a defect).** The reviewer could not see whether the later `actions/checkout` of `opencharly/action-review` would clean away the arm's directories, because the diff it read was truncated. *Answer:* `actions/checkout` cleans **only the directory it manages** — inside its own `path:`. Every checkout in the `validate` job carries a `path:`: the tree under judgement is `repo`, the review's config is `runner-config`. The arm's `contract/` and `org-rules/` are **siblings** of `runner-config/`, not inside it, so they survive; and the review step reads `runner-config/` and the GitHub API, never `repo/`. *Root fix:* the checkout now carries that boundary as a comment on itself, and this body answers it.

**Also fixed in round 2 — an R2 duplication I found myself.** The arm's coverage and the head-settle coverage each carried their **own copy** of the awk that extracts a shipped step's `run:` text — byte-identical. Two copies of one rule is how the copies drift. The extraction now lives **once**, in `scripts/lib-org.sh`, and both tests call it.
