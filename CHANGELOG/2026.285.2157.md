# 2026.285.2157 — feat(bootstrap): a new repo enters the gate, or the gap is loud (#180)

## Summary

A session-created repo did not inherit the org's settings, and every symptom of that was **silent** (`opencharly/.github#180`). Three of them were measured on live instances:

1. **The default branch stayed the first-pushed `feat/...`** — so the repo fell into `discover_excludes`: no required `validate / validate` check, no CalVer tag, no `CHANGELOG`. Nothing transitions it back.
2. **The tag-on-merge caller arrived with the first PR — and could never fire for that first merge**: the `charly/pr-validator` run completed before the file existed on `main`, and GitHub creates ZERO runs for an auto-merge squash. Two sessions hit this independently (`plugin-generate-podcast`, `layer-podcast-audio`) and repaired it by hand afterwards (both now carry the caller and have tags — verified).
3. **The bootstrap run reported `success`** while 1 and 2 were true.

This change closes the loop that *can* be closed in-tree and makes the rest **loud**:

- **`scripts/bootstrap-repo-main.sh`** now installs the org's **canonical, pinned** `tag-on-merge.yml` dispatcher on every `main` it creates, via the contents API — the capability the same App token already uses to write `CHANGELOG/<CalVer>.md` to protected `main` (20 of the last 40 commits in this repo are its CHANGELOG writes). The install is **asserted by reading the file back**, so a "reported success, nothing on main" path is impossible. The script then prints the three repository SETTINGS it cannot set and counts them: `needs_operator_settings=<n>`.
- **The three settings stay an operator action, and that is now measured, not assumed.** The `charly-auto-merge` installation's live permissions are `actions, contents, deployments, issues, merge_queues, metadata, packages, pages, pull_requests, repository_custom_properties, workflows` — **no `administration`** — so `PATCH /repos/...` is genuinely 403 for the App.
- **`scripts/org-ruleset.sh verify` gains a MEMBERSHIP-INTEGRITY arm.** The target set is *defined* by `defaultBranchRef == "main"`, so the existing per-repo loop could never notice a repo that fell out of it. The arm now fails on any active, non-fork repo whose default is not `main`, unless it is declared with a reason in `lib-org.sh`'s new `declared_non_main_defaults()` — the two by-design entries (`omarchy-eval-artifacts`/`runs`, `pixelflux`/`av1`) that `/charly-internals:repo-setup` names. It prints a remedy that matches the sub-case (a `PATCH` when a `main` ref exists; **bootstrap-then-PATCH** when none does), names an empty repo distinctly, and refuses to report a clean membership from a failed read.

**Consequence, stated before the push.** On the live org the arm fails on **exactly two** repos — `plugin-task-old-16365` and `plugin-task-zzbootstrap` (both `default: feat/plugin-task`, no `main` ref, **0** rules on `main` vs `charly`'s 5) — until they are archived or bootstrapped. Both are abandoned bootstrap experiments; the disposition is operator-owned (archiving is effectively permanent) and is filed as `#193`. Three empty probe repos (`zz-probe3-7319`, `zz-probe2-13988`, `zz-bootstrap-probe-xyz`) are named informationally, never failed: an empty repo cannot merge anything, and the moment it has a branch the arm fails.

Closes #180.
