# 2026.296.1024 — fix(ci): only the current head may write the review comment

## Summary

A push during a review makes that run stale. Its comment upsert is last-writer-wins, so the OLDER review can land after a newer one and leave the comment describing a head that no longer exists — the review then looks like it did not update on the push.

The comment step now reads the PR's current head and, when it has moved past the head this run reviewed, leaves the comment to the newer run:

```bash
current_head="$(gh api "repos/${GITHUB_REPOSITORY}/pulls/${PR_NUMBER}" --jq '.head.sha')"
if [ "${current_head}" != "${REVIEWED_HEAD}" ]; then
  echo "::notice::the PR head moved … leaving the comment to the newer run"
  exit 0
fi
```

Callers should ALSO cancel the superseded run (`concurrency:` + `cancel-in-progress: true`, which needs `actions: write`); this is the backstop for callers that cannot grant it. The two together are what make the comment always describe the current push.

## How tested

The guard is a pure comparison against the live PR head, exercised by every run of the caller. The caller side is already in use: `opencharly/crabbox#17` declares

```yaml
concurrency:
  group: clawsweeper-review-${{ github.event.pull_request.number }}
  cancel-in-progress: true
```

and its runs on successive pushes show a single review per head.

## Rulebook compliance

| Rule | How it is honoured |
|---|---|
| R1 | The stale-write race was named from observed behaviour (comments describing an older head, and the duplicate-run poison on the required gate). |
| R2 | One comment per PR, one writer: the newest run for the current head. |
| R3 | No retry and no sleep: a stale run simply does not write. |
| R7 | Exercised by the caller's runs; the guard is a direct comparison against the live API. |

## Change classification

Reusable-workflow change to the comment step only. Callers need no change; callers that ALSO set concurrency get cancellation rather than a skipped post.
