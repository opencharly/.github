# 2026.282.2309 — feat(org): detect PRs whose auto-merge is armed but which can never land (#175)

## Summary

`opencharly/.github#175`'s RCA is precise: **native auto-merge armed + the org ruleset's `strict: true` required checks + a `BEHIND` head = a silent stall**, measured over ~10 h on 2026-10-07/08 with **zero landings** while at least seven PRs sat green or armed. The issue ends with the line that makes this fix small:

> The state is already one API field away; nothing today reads it.

So this adds the reader. **Not a missing capability — a missing reader**, which is why the change is one script and one thin workflow.

```console
$ grep -rln "mergeStateStatus\|autoMergeRequest" scripts/ .github/     # before this PR
$                                                                       # nothing
```

## What it adds

- **`scripts/check-stalled-automerge.sh`** — one org-wide GraphQL read (`org:opencharly is:pr is:open`) projecting exactly `autoMergeRequest` and `mergeStateStatus`, then the selection rule the RCA names: `autoMergeRequest != null AND mergeStateStatus == "BEHIND"`. It prints each stalled PR **with the remedy** and exits 1; nothing stalled exits 0; **a failed query exits 2 rather than reporting "nothing stalled"** — a detector that reads green off a failed read is worse than none.
- **`.github/workflows/stalled-automerge-detector.yml`** — every 30 minutes plus `workflow_dispatch`, through the `charly-auto-merge` App token the landing chain already uses, so **no new app grant is introduced**. The alarm is a **red run**: visible in the Actions tab, and one scheduled job instead of a hook installed in ~400 repos.

## The scope limit, in the script rather than left to be discovered

This detects the shape the RCA measured and **nothing else**. A `CANCELLED` required check — a superseded validator run leaves `validate / validate` cancelled and the PR `BLOCKED` with auto-merge never armed — is a *different* shape with a different remedy, is not covered, and is not claimed to be. Not hypothetical: it is what `opencharly/charly#871` showed earlier today. Naming the uncovered shape is the difference between a detector and one that gets trusted for more than it does.

## How tested

```console
$ bash -n scripts/check-stalled-automerge.sh                       # rc=0
$ bash scripts/check-stalled-automerge.sh --self-test
check-stalled-automerge: self-test ok                             # rc=0
$ bash scripts/check-stalled-automerge.sh                         # the real org scan
check-stalled-automerge: no armed+BEHIND PRs in opencharly — nothing is silently parked   # rc=0

$ python3 .github/tests/validator-gate-harness.py
ALL PASS: 414 assertions across 23 scenarios, run against the real workflow run: bodies.
$ bash scripts/org-ruleset_test.sh
org-ruleset_test: all assertions passed (apply/verify/abort)
```

**The self-test drives the STALLED branch, not only the filter.** `report_stalled` is extracted from `main` so the alarm — the `exit 1` and the remedy loop that IS this change's product — is executed by a test. The first version exercised only the pure filter, and the live scan took the **exit-0** branch: a true negative proves nothing about the alarm. The assertion is **proven able to fail**: mutating the remedy line makes the self-test report `the stalled branch did not emit its remedy`.

**And the earlier third assertion is REMOVED, not reworded.** The reviewer was right that "the filter can never select nothing" cannot fail independently — a filter that selects nothing already fails the first assertion. A redundant check that cannot fail on its own is exactly what R7 calls invalid, so it is gone rather than dressed up.

**The rest of the first version's evidence, which still holds:**

**The self-test is the R7 evidence, and it is built to be able to fail.** It asserts an armed+`BEHIND` fixture **is** selected; that three near-misses are **not** (armed but `CLEAN`; `BEHIND` but unarmed; unarmed `BLOCKED`); and — the assertion that keeps the whole detector honest — that the filter does **not** select nothing, because a selection rule that can never select is a green no-op. **For a detector, "it selects nothing and always passes" is the failure to guard against, so the guard is an assertion of its own.**

The live scan is a **true negative** — nothing is parked in that shape today — which is exactly why the fixtures, not the org, are what proves the rule.

## A reviewer note, rebutted with evidence

The security screen's only note was that `actions/checkout@v7` is a floating tag "inconsistent with that pinning discipline". That is **this repo's own convention, not an oversight**: `actions/checkout@v7` appears **9 times** across `.github/workflows/`, and the SHA pinning discipline it is being compared to applies to third-party actions (`create-github-app-token` is pinned, and so is it here). Matching the repo is the correct behaviour; pinning one of nine would be the inconsistency.
