## feat: pr-validator orchestrates merge; remove separate auto-merge workflow

### The change

The pr-validator now does the whole flow on PASS:
1. AI review (pi-review-action v1.0.8, retries on empty responses)
2. Rename the CHANGELOG placeholder to the merge-time CalVer
3. Dispatch a fresh validator run on the new head (`workflow_dispatch`)
4. Enable GitHub's native auto-merge (`enablePullRequestAutoMerge`)

The separate auto-merge workflow is **removed** — GitHub's native
auto-merge (repo setting + branch protection) does the actual merging.

### Why the dispatch is needed (verified against GitHub docs)

The CHANGELOG rename push uses `GITHUB_TOKEN`. Per GitHub docs,
GITHUB_TOKEN-triggered `pull_request: synchronize` events create
workflow runs in an **approval-required** state — not automatic runs.
So the validator would NOT re-run automatically on the renamed head.

`workflow_dispatch` is the documented exception: it **always** creates
workflow runs, even from GITHUB_TOKEN. The dispatch targets the
dispatcher (on the default branch after this PR merges) with a
`pr-number` input. The reusable validator fetches the PR via the API
(no `github.event.pull_request` dependency), so the dispatched run
works without a pull_request event context.

The `charly/pr-validator` failure on the current head is from the
**old** reusable validator (on main) which reads
`github.event.pull_request` — a `workflow_dispatch` run has no
pull_request context, so it fails with "No pull_request context".
This PR's new reusable validator uses the `pr-number` input and
fetches the PR via the API, so the dispatched run works. The old
reusable is replaced by this PR.
