# 2026.255.1029 — validator: pass AI_REVIEW_ATTEMPT_TIMEOUT through (org-settable) + correct the guardrail RCA

## Summary of changes

Two coupled edits in the org-wide merge guardrail, `.github/workflows/pr-validator.yml`, plus its in-repo coverage.

**(a) Pass the review attempt cap through — the fix.**

`plugin-review` has always read an attempt cap: `candy/plugin-review/review.go:102` parses `AI_REVIEW_ATTEMPT_TIMEOUT` (**seconds**) into `cfg.AttemptTimeout`, which becomes the review's `http.Client{Timeout}` (`candy/plugin-review/llm.go:80`); the built-in default is `defaultAttemptTimeout = 5 * time.Minute` (`review.go:28`). This workflow passed every other `AI_REVIEW_*` value but never this one, so every org run was pinned to 5 minutes per request and **no operator could raise it without a code change** — the no-verdict signature measured in **opencharly/.github#91** (~20m43s, exit 1, required check RED). One env entry fixes that:

```yaml
AI_REVIEW_ATTEMPT_TIMEOUT: ${{ vars.AI_REVIEW_ATTEMPT_TIMEOUT || '900' }}
```

- **Operator lever:** org-level variable `AI_REVIEW_ATTEMPT_TIMEOUT` (Settings → Secrets and variables → Actions, visibility all — the same place as the other `AI_REVIEW_*` values), in seconds. No code change, no consumer-repo change.
- **Why the default is generous (900 s = 15 min):** the measured failure is a slow *legitimate* large-context generation, not a hang. The cap bounds ONE `http.Client.Timeout`, and plugin-review's attempt count is its own fixed 3, so the worst case stays bounded (3 × cap). The old 5-minute behaviour stays reachable by setting the variable lower (e.g. `300`).
- **No retry, no sleep (R4):** the workflow still retries nothing; it stops discarding a value the plugin already reads.

**(b) Correct the guardrail RCA — required for internal consistency with (a).**

The workflow header still carried the superseded **2026-09-11 "throttled datacenter egress"** diagnosis, which explicitly stated that *"Neither a longer AI_REVIEW_ATTEMPT_TIMEOUT nor an in-job retry can cure this"* — i.e. it disclaimed the exact knob (a) adds. The corrected RCA is recorded in **opencharly/.github#91**: the request is **non-streaming** (`llm.go:92`, no `stream:true`), so response headers arrive only after the whole generation, all under one `http.Client{Timeout}`; the review runs a **20-turn tool loop** that appends every turn's tool results (the PR diff/files) to the context and retries the **whole loop** 3 times — so **turn 1 completes and turn 2 — carrying the enlarged context — fails in ONE OF TWO OBSERVED ways**: it returns **EMPTY content** (`turn 2: final content len=0`, `review_len=0`; observed on **2 of the 3 attempts** in run 34682776608) **or** it **exceeds the 5-minute cap** (`Client.Timeout exceeded while awaiting headers`; observed on the third). Both are one defect class — an unbounded, non-streaming request whose context grew — and the fix covers both. The earlier text here claimed the deadline occurred *"identically on all 3 attempts"*, which contradicted this PR's own pasted log; corrected. The endpoint was never the problem (it answered 405 in 0.18 s in the same window, and the runner received a complete turn-1 response). Contributing client-side defects: no explicit `http.Transport`, unbounded tool-result payloads, and a whole-loop retry. The same false RCA was also **posted on every INCONCLUSIVE PR** by the `Gate (inconclusive)` comment body — corrected there too, and the invented "validator-egress hardening batch" remedy is **deleted, not parked**.

## Scope extension — the engine-change exception + the engine-defective class (opencharly/.github#97)

Per the RCA in opencharly/.github#97 (8 steps), this PR now also carries the root fix for the structural gap the review-engine defect exposed: the validator fetches the review engine from a fixed ref, so a PR to the engine is graded by the pre-change code and a defective engine blocks every verdict org-wide with no documented exception path.

1. **`T13` (policy, symmetric to T4).** A change to the review engine itself cannot be independently reviewed by that engine; it requires the **maintainer's sign-off recorded on the PR** and an **operator-performed merge**. The clause states explicitly that this is **NOT a bootstrap** — serving the engine from the PR head would let a PR rewrite the gate so that it approves itself, destroying the independence the fresh validator exists to provide — and that it is **never `gh pr merge --admin`** and never an agent-performed bypass.
2. **`engine-defective` (diagnosability).** The review step now classifies the context-dependent failure (turn 1 COMPLETED — so the endpoint answered — and a later turn failed or returned empty content) and the INCONCLUSIVE notice reports that named class instead of every verdict-less run being labelled `provider unanswered`. That is the implementable half of the issue's ask: a defective engine is diagnosed by name, with the engine ref, the failing signature and the T13 remediation pointer, rather than burning 15–20 minutes and reporting a misleading cause. (A dedicated canary probe was not added: a probe that reproduces a context-dependent turn-2 failure would be a mini-review, i.e. the same cost as the run itself — so the classification is derived from the real run's own signature, which is exactly the evidence the class needs.) **Coverage (R10):** the class's SELECTION is asserted FUNCTIONALLY, not by a source-text match — the harness gained an `engine-defective` scenario whose fake review log carries a completed `turn 1: 4 tool call(s)` PLUS a provider marker, forcing the classification's true branch; its assertions require the posted INCONCLUSIVE notice to name the class (`engine-defective (the review engine`, `T13 engine-change exception`) and the review output to carry `engine_defective=true`. PROVEN load-bearing: against `origin/main`'s workflow those assertions FAIL (`engine_defective=None == expected 'true'`, and the class absent from the posted comment); on this tree all 103 assertions across 8 scenarios pass.
