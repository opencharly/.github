# 2026.314.1425 — fix(ci): verify a created tag by its ref, never by the tags listing

## Summary

`opencharly/.github#298`. The missing-tag backfill's first live pilot (`#297`'s merge-time run) tagged all three heads and reported a **failure** for one of them. The tag was correct; the **read-back** was wrong.

**Mechanism.** `head_tag()` verified a create by scanning the tag **listing** (`repos/<repo>/tags?per_page=100`). A listing lags a create, and it lagged this one: the run's immediate re-read did not see the new tag, the read-back failed, and the run counted a failure for a tag it had just created — and exited non-zero.

A listing is a **census**; a ref read is an **identity** check. A create must be verified with the latter.

**What changed** (2 files, +70 −6):

1. **`ref_points_at()`** — a point read, `gh api repos/<org>/<repo>/git/ref/tags/<tag> --jq '.object.sha'`, compared against the head. The listing scan stays for the **pre-check**, where a lag costs only a redundant create that add-only already guards.
2. **A create that LOSES to an existing ref** (HTTP 422 — the pre-check's own listing had lagged) is no longer reported as a failed create. The run asks the point read which commit the ref holds, which is the only question that matters, and reports `already present at the head`. **Add-only is untouched:** on a 422 the script READS the ref and never writes it, so no tag is ever overwritten.
3. **A ref that exists at a DIFFERENT commit is a hard failure.** That arm is what keeps (2) correct rather than permissive: without it, "the ref exists" would report a tag on the wrong commit as success.
4. Failure output now carries `gh`'s own stderr instead of discarding it, so a real API error is legible in the run log.
