# 2026.255.1742 — fix(validator): preserve the review evidence + give a provider HTTP rejection its own class

## Summary

Fix **both halves** of the PR-eval failure path: it could neither **name** a provider rejection nor **preserve** the evidence of one.

**Two behaviours accounted for, both load-bearing:**

- **`continue-on-error: true` on both `if: always()` reporting steps.** Their purpose is that a reporting failure must never turn a PASS run RED — the workflow's own comment says so, and the harness now models GitHub's semantics and covers it: `pass-with-unwritable-evidence` fails the evidence step (unwritable `RUNNER_TEMP`) and asserts the job **keeps** its PASS verdict and its armed auto-merge. With that handling disabled the scenario fails `job exit 1 == expected 0`.
- **`actions/upload-artifact`**, pinned to the commit behind its `v4` tag (`ea165f8d65b6e75b540449e92b4886f43607fa02`) — the tightest form this org already uses elsewhere (`actions/create-github-app-token` in `tag-on-merge.yml` is SHA-pinned). It adds **no secret and no permission** (the artifact service uses the job's own runtime token), and `if-no-files-found: ignore` keeps a missing bundle from failing the step.

**Coverage this PR adds** (all asserted by the committed harness, which runs the workflow's real step bodies):

- **`provider-error`** — the outage's own signature: a log carrying `LLM 400` and no verdict must be classified as a provider rejection, with its own narrative, and must NOT carry the retired streaming story.
- **`non-error-status`** — the **boundary** of the extractor: a verdict-less log carrying a NON-error status (`LLM 200`) must NOT be classified as a rejection. The final commit narrows the pattern to `[45][0-9][0-9]`; with the previous `[1-5][0-9][0-9]` this scenario fails (`provider_error='200'` and the comment carrying *"provider rejected the request"*).
- **`mixed-signals`** — a completed turn 1 **and** an HTTP rejection in one log: the **composed** class must win (`provider rejected a LATER request (HTTP 400) after turn 1 completed — the enlarged-context class`), and the notice must NOT claim the engine never ran a turn.
- **`unanswered-plus-error`** — a stall marker **and** an HTTP rejection with **no** completed turn 1: the case where the plain provider branch printed a denial its own class inputs contradicted (`PROVIDER_UNANSWERED` was true). The composite branch describes both signatures instead.
- **`pass-with-unwritable-evidence`** — the `continue-on-error` contract made executable: the evidence step fails (unwritable `RUNNER_TEMP`) and the job **keeps** its PASS verdict and its armed auto-merge — `job exit 0`, not a red check on a PASS run.

All five scenarios added by this diff are named here, and every figure above comes from the single harness run pasted in "How tested" on this head.

Two harness capabilities back that up: **`expect_comment_excludes`** (a misattribution is invisible to a positive assertion) and **`expect_summary_contains`** (a Summary claim is only proven by reading what it wrote).

            must be diagnosable from the gate's own output.

**Mechanism proven, not inferred** — three controlled requests against the live gateway with the org's key:

|---|---|
| `/zen/go/v1/chat/completions` plain | **400 MissingSessionID** |

The protocol half of the root cause is fixed in **`plugin-review#8`** (send one session id per run). **This PR fixes the gate half.**

### Fix 1 — the class and its cause now agree

The review step extracts the provider status from the log (`LLM <4xx|5xx>`) and the notice gained a class for it. The ladder is ordered **most specific first**: the composite `engine-defective + provider-error`, then `provider-error + provider-unanswered`, then the plain provider rejection — each stating only what its own inputs prove:

`class: provider rejected the request (HTTP 400) — a provider/protocol/config matter, not an engine verdict`

The narrative is now **class-aware**: each branch states the cause *its own* evidence supports. The rejection branch says explicitly that the streaming and no-headers classes **do not apply** (the engine never ran a turn) and that an HTTP rejection is **deterministic** — so a blind retry is the wrong response. The other classes keep their text unchanged.

### Fix 2 — the evidence survives

An `if: always()` **evidence bundle** now runs on every outcome, including failures:

- **Artifact `validator-evidence`** — the **FULL** `review.log` plus the verdict files (`review.txt`, `review.untrusted.txt`) and a `.absent` marker for any that is missing (an absent file is itself evidence: a 3-line log means the review never started; 500 lines means it ran and failed partway). Retention 14 days.
- **Machine-readable `manifest.txt`** — the class inputs, the exit code, and the **effective** `AI_REVIEW_PROVIDER` / `MODEL` / `BASE_URL` / `ATTEMPT_TIMEOUT` and `CHARLY_VERSION`. That is the question everyone had to answer by hand on 2026-09-12.
- **The run's own Summary page** — the same class/config table, so a reader opening a red run sees *why* without a PR-comment round trip or a log hunt.

### Fix 3 — the harness now models GitHub correctly

The harness ended the job at the first failing step (*"the job stops here, exactly as GitHub would"* — it does **not**). That is why an `always()` step was untestable. It now models the real semantics: a failed step does **not** end the job; `always()` runs; a plain or absent `if:` carries an implicit `success()` and is skipped. The evidence step is therefore exercised on **every** scenario — including the failing ones, which is the point.
