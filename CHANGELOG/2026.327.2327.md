fix(labels): per-issue audit scope, and an issues-disabled class that is not a failure

Closes opencharly/.github#318 and opencharly/.github#315.

**#318 — one issue at a time, one parser.** `audit` gains `--issue owner/repo#N`: it narrows the
repo set to that repo, reads its issues, and evaluates ONLY that number — so a form answer is
applied by the SAME mapping the full audit uses (no second parser), one repo read instead of
446. `label-audit.yml` gains an `issues: [opened, edited, reopened]` trigger calling it, so an
issue in THIS repo is labelled at creation under the same `LABELS_AUDIT_APPLY` policy.

The org-wide limit is now stated in the workflow: the org ruleset activates its required
workflow on **pull_request** events only, so an `issues` trigger in this repo cannot fire in
other repositories. Org-wide the daily full-org audit remains the applier; this repo gets the
immediate path as its own first consumer.

**#315 — "has disabled issues" is a property, not a failure.** `api_error_class` returns a new
class `2` for `the '<repo>' repository has disabled issues` (a repository property, not an API
refusal); `cmd_retire` treats it as `count=0` and names it ONCE per repo instead of emitting
`request failed` per retired label. Measured on the 2026-11-23 retirement: nine `request
failed: Qwen3-TTS` warnings for one issues-disabled repo, all unactionable.

Tests (`scripts/labels-test.sh`, now 24 arms):

- `audit --issue opencharly/repo1#10 --apply` applies exactly the issue's form answer and
  touches no other issue; a form-less issue is reported and applies nothing; a malformed
  `--issue` dies.
- a repo with issues disabled: `retire --dry-run` exits 0, names the state ONCE, never prints
  `request failed`, and still plans the deletion.
