# 2026.296.1323 — fix(ci): arm against the mutation, not against a proxy merge state

## Summary

The `arm` job no longer waits for `mergeable_state == 'clean'` before arming. It attempts
`enablePullRequestAutoMerge` directly and tolerates **only** GitHub's named
`is in unstable status` refusal, inside a bounded 180 s window. Everything else fails at once,
exactly as before. `validate` and `lint` and the whole of gate B are untouched.

## The RCA — why `#238`'s wait could never succeed

`#238` was written on the theory that GitHub's merge state lags its own check runs, and that
polling `mergeable_state` until `clean` closes the gap. It does not, because `mergeable_state` is
computed over **every check run on the head — including the `arm` job's own**. That check run is
`in_progress` for precisely as long as the job waits. So the condition is unsatisfiable by
construction, the poll always ran its full budget, and the mutation afterwards was refused with
the same error `#238` set out to remove.

Measured on `crabbox#17`, same head `85530224`, two attempts three hours apart:

```console
$ gh api repos/opencharly/crabbox/actions/runs/39953828303/jobs \
    -q '.jobs[] | select(.name|test("arm")) | "\(.name) \(.status) \(.conclusion)"'
validate / arm  completed  failure          # attempt 1 — 27m42s
validate / arm  completed  failure          # attempt 2 — re-run of that job only
```

```console
$ gh api "repos/opencharly/crabbox/commits/85530224.../check-runs?filter=all" \
    -q '[.check_runs[].conclusion] | group_by(.) | map("\(.[0]): \(length)") | .[]'
failure: 2
skipped: 1
success: 34
```

The two failures are `validate / arm` itself, i.e. the consequence. Everything else on the head
is green (34) or skipped (1). The second attempt is the falsifiable test: the same code, the same
head, the same refusal — so the mechanism is structural, not transient.

The **missed control** was mine: `#238` shipped on a single observation (a mutation refused one
second after gate B went green) without a second run to distinguish "lag" from "self-reference".
A fix for a race is not proven until it has been run against the case that produced the race.

## Round 1 — the loop had a hole, and it was a real one

The BLOCK on the first head was correct: the retry loop read the PR **once** before entering and
then reused that `pr.id` for up to 180 s. `enablePullRequestAutoMerge` takes a pull-request ID, not
a head SHA, so a push arriving inside the window could be armed, and the post-arm check only
noticed after the fact — leaving auto-merge armed on a head nobody reviewed. My body's claim that
"a moved head fails at once, unretried" was false, and that claim was the defect.

Fixed in this round:

- `armHead()` re-reads the PR and verifies `headRefOid` and `state` immediately **before every**
  mutation attempt;
- a retry that finds auto-merge already armed stops instead of mutating again;
- if the head has moved when arming completes, auto-merge is **disarmed** before the job throws.

## Why this is still a bounded condition-wait, not a blind retry

- It is reachable only after gate B has proven every check run on the head green, its own
  excluded by name. The retry cannot paper over a red job.
- It fires on one named, documented server response and on nothing else. Auth failures, a moved
  head, a real block: all thrown immediately, unretried.
- It is wall-clock bounded, and it says so when the budget is exhausted instead of silently
  proceeding to a confusing error.
- The success is verified afterwards, as before, by re-reading `autoMergeRequest.mergeMethod`.
