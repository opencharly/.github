# 2026.313.1651 — fix(ci): an untagged merge now reddens tag-on-merge and NAMES the PR

An untagged merge is now loud: `tag-on-merge` ends with a step that asserts every merged PR in its sweep window resolves to a tag **at its merge commit**, and fails **naming the PR** when one does not. `opencharly/.github#286`'s own failure — the step dying inside a transient 5xx before it wrote anything — is covered too, because the assertion runs on a non-cancelled condition, i.e. **after a failed step**.

## Summary

The sweep could leave a merged PR untagged in two ways, and neither was visible to anyone but the person who happened to ask:

- **SILENT** — in sweep mode each per-PR failure is caught and downgraded to a `core.warning` that prints the error and logs `— continuing`, so the step exits 0 with the merge untagged. A green run therefore does **not** mean "every merge is tagged".
- **FATAL** — a transient 5xx or socket reset aborts the step before any tag is written (`#286`'s own evidence: `HttpError: other side closed` in the listing read). The next step would be skipped, so the untagged merge stays unnamed even though the run is red.

The new step is the post-condition of both, and it derives **no CalVer**: it asks only whether each merge commit carries **any** tag, so it cannot drift from the naming rules in the step above (root CalVer, the Go-module form, the subdir module tag). An annotated tag is dereferenced to its commit — comparing against the tag object would be a false negative for every annotated tag in a repo that carries one.

The window is now **one** literal, the job's `SWEEP_WINDOW_HOURS`, read by both the sweep and the detector. Two literals would let the detector judge a population the sweep never acted on. A missing or non-numeric value fails the run rather than defaulting to an empty window, which would report "nothing to tag" forever.
