# 2026.241.1625 — fix(scripts): apply+verify repo-level allow_auto_merge — closes the validator auto-merge gap

## Summary

Closes the org-wide validator auto-merge gap (hit live while landing #437 and #456: pod-hyprland#2 and charly-streamer#2 both posted a PASS verdict yet stayed BLOCKED).

**RCA:** the org-wide `charly/pr-validator` workflow's PASS enables native auto-merge via GraphQL `enablePullRequestAutoMerge`. On repos where the repo-level **`allow_auto_merge`** setting is off, that call fails with `"Auto merge is not allowed for this repository"` — the review action already posted `Verdict: PASS`, but the check run goes red and the PR stays BLOCKED (mergeStateStatus BLOCKED). New GitHub repos default the setting to **off**, and the org tooling never enforced it: branch-protection.sh (the documented "single organization-wide owner" of the merge gate) only managed the ruleset. A live sweep found **13 of 368** org repos affected.

**Fix (in the canonical owner, dotgithub/scripts/branch-protection.sh):**
- **apply** now PATCHes `allow_auto_merge=true` on every active repo (no-op when already on)
- **verify** now asserts `allow_auto_merge == true` per repo and fails otherwise — so a regression is caught, not just fixed once

The 13 affected repos were already re-enabled during the #437 landing; this change makes the invariant durable and owned.

## How tested

The rewritten unit test mocks the GitHub API (rulesets list/detail/create, legacy-protection probe, repo settings GET/PATCH) and asserts: apply PATCHes the false repo to true and leaves the already-true repo untouched; verify passes after apply; verify FAILS when the setting regresses. (The previous test mocked a deleted legacy API path and could not run against the current ruleset-based script.)

Live verify run against the org: exit 0, 363 repos verified, 0 auto-merge violations.
