## Summary

The org ruleset (23827016) requires exactly **ONE** context, `validate / validate`. A repo's own `ci` was therefore enforced by **nobody**: rulebook ground rule 5 and checklist item B18 both told the reviewer that "branch protection enforces the repo's required checks", and branch protection did not. Two merged heads prove the cost:

- **charly#795** — `go` FAILED at `02:35:42Z`; the review PASSed at `02:44:58Z`, **9m16s later**, and the merge landed at `02:45:21Z` on that already-red head.
- **charly#791** — the merge landed at `21:25:04Z` while `go` was **STILL RUNNING**; `go` then failed at its `Test` step at `21:27:24Z`, **2m20s AFTER the merge**. #791 is why this gate WAITS rather than takes a snapshot: at gate time the doomed check was `in_progress`, not `failure`.

Two deterministic gates now run **inside** the required check, after the verdict gates and before auto-merge is armed. They gate **arming auto-merge only** — the review, its comment and the auto-close counter are untouched.

**GATE B — every check run on this head.** Reads the head's own check-run conclusions off the API and fails on any that did not pass, **waiting** (bounded, 600s) for in-flight ones to settle first — the review is FASTER than the repo's own CI in 4 of 5 sampled PRs (`validate` 0m40s–14m15s vs `go` 3m57s–5m11s), so failing closed the instant a check is pending would block most PRs. Generic by construction: no linter, no checkout, no per-repo coupling.

It reads `filter=all` and takes `max_by(.id)` per (name, app) — **not** `filter=latest`. Measured against the live API, `latest` **drops the check name entirely** during a re-run:

```
01 latest=[] all=[completed,completed,completed,completed,completed,completed]
02 latest=[] all=[completed,completed,completed,completed,completed,completed]
03 latest=[queued] all=[queued,completed,completed,completed,completed,completed,completed]
```

A gate reading `latest` sees an EMPTY check set in that window and arms auto-merge on a head whose check is mid-re-run — the #791 hole re-opened. With `filter=all` + `max_by(.id)` the name is never absent (check-run ids are monotonically increasing, verified). It excludes itself by `details_url` **and** by the required context's name, so it can never count its own `in_progress` check run.

**GATE A — the repo's DECLARED lint.** Gate B cannot see a repo that declares a lint policy nothing runs (measured: `plugin-check` carries `.golangci.yml` and its only workflow is `tag-on-merge.yml`). Gate A runs golangci-lint over each Go module root that has a declared config and **skips the rest**, because falling back to golangci-lint's standard set would impose a NEW gate on repos that never linted — measured, **6 of 8** sampled unconfigured org repos fail that standard set. Config selection is the subtle part: the repo-root config governs every module; otherwise each module uses its own by walk-up; with neither, SKIP. `GOWORK=off` always, because charly's 5 `tools/*` modules are not members of `charly/go.work`.

**Rulebook reconciliation, same repo.** Ground rule 5 and B18 in `charly.yml` stated the false branch-protection premise; both now state the true mechanism and point at the gates. `scripts/governance-claims.tsv` gains a `ci_gate_mechanical` claim pinning both gates, the `filter=all` read, and the `checks: read` grant, and forbidding the retired premise. The offline harness gains a fake-`curl` sub-test that runs the REAL gate-B body over all four of its branches.

**Permission added:** `checks: read` on the reusable **and** on the org-wide required caller (`checks` is its own scope, and a called workflow can only hold what its caller grants). That is the only permission added anywhere.
