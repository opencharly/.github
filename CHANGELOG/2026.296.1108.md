# 2026.296.1108 — fix(ci): wait for a clean merge state before arming, not just for green checks

## Summary

MEASURED on `crabbox#17`. Gate B read, verbatim:

```
all 33 check run(s) on this head passed — safe to arm auto-merge      11:05:42Z
```

and the arming mutation **one second later** failed:

```
GraphqlResponseError: Request failed due to following response errors:
 - Pull request Pull request is in unstable status                     11:05:43Z
```

GitHub's own merge state lags its check runs. The new non-required `arm` job hit that window and went red; the required `validate / validate` correctly stayed green — the split did its job, but arming is the one thing that job exists to do.

**Fix.** Before the mutation, the step waits — bounded at 120 s, polling every 3 s — for the REST `mergeable_state` to reach `clean`, and logs what it saw. This is the same *condition-wait* gate B already performs, against the other API: bounded, for a named condition, never a blind retry. If the state never becomes clean within the budget, the existing mutation error still surfaces unchanged.
