# 2026.240.2243 — fix: the dispatcher templates deadlock any repo onboarded from them

## Summary

**The dispatcher templates in this repo would deadlock any repo onboarded from them.**

`org-wide-pr-validator-dispatcher.yml` declared its caller job as:

```yaml
jobs:
  pr-validator:
    name: charly/pr-validator
```

A check run produced by a **reusable-workflow call** is named
`<caller job name> / <called job name>`. The called job in
`.github/workflows/pr-validator.yml` is `validate`, so that template yields the check
**`charly/pr-validator / validate`**.

`scripts/branch-protection.sh` requires exactly:

```sh
readonly CONTEXT="validate / validate"
```

A repo onboarded from the template therefore gets a ruleset demanding a check that **can never
appear**. Its PRs stay `BLOCKED` forever and it can never merge anything.

## Why this is latent rather than actively breaking

Every repo already in the org runs a **different** dispatcher — job `validate`, name `validate` —
which is why the org works today. The live file is byte-identical across four sampled repos, so
it is the de-facto standard and the template had simply drifted from it:

```
$ for r in spec sdk plugin-vm pod-waybar; do gh api …/pr-validator.yml | base64 -d | md5sum; done
11aa338d6767      (spec)
11aa338d6767      (sdk)
11aa338d6767      (plugin-vm)
11aa338d6767      (pod-waybar)
```

Same for `tag-on-merge.yml` (`9886d8e44dc2` across all four).

## The fix

Both templates are replaced with the live file **verbatim**, so a copy-paste onboard now produces
exactly what the org runs:

```
$ diff <(tail -n +8 org-wide-pr-validator-dispatcher.yml) <(live pr-validator.yml from spec)
pr-validator body: IDENTICAL to what every repo runs

$ diff <(tail -n +4 org-wide-tag-on-merge-dispatcher.yml) <(live tag-on-merge.yml from spec)
tag-on-merge: IDENTICAL
```

The pr-validator template also **regains the `workflow_dispatch` + `pr-number` input** the live
one carries and the template had lost — that is the path used to re-run a validator on an
existing PR, so its absence would have been felt immediately by anyone onboarding from it.

The header now states why the job name is load-bearing, so the next edit cannot silently
re-break the required-check contract:

```yaml
# Copy VERBATIM into every repo. The job MUST stay named `validate`: the branch
# ruleset requires the status check `validate / validate` (scripts/branch-protection.sh
# $CONTEXT), and a check run from a reusable-workflow call is named
# `<caller job name> / <called job name>`. Renaming this job renames the check, the
# required check then never appears, and the repo can never merge.
```

## How tested

The context-composition rule is **measured, not assumed**:

```
called workflow job (.github/workflows/pr-validator.yml):   validate
live caller job (opencharly/spec):                          validate
observed check on opencharly/spec#64:                       validate / validate
```

That confirms `<caller job name> / <called job name>`, which is what makes the old template's
`charly/pr-validator` job fatal rather than cosmetic.

Both templates parse:

```
$ python3 -c "import yaml; [yaml.safe_load(open(f)) for f in (…both…)]"
both templates parse as valid YAML
```

And the job name now matches the required context:

```
$ grep -A2 '^jobs:' org-wide-pr-validator-dispatcher.yml
jobs:
  validate:
    name: validate
$ grep -n 'readonly CONTEXT' scripts/branch-protection.sh
7:readonly CONTEXT="validate / validate"
```
