# 2026.265.0712 — feat(validator): invoke the review engine directly + auto-close after N BLOCKs

## Summary

Three coupled changes to the org-wide `charly/pr-validator` workflow.

### 1. Direct engine invocation (drop the `--plan` executor)

`charly review --plan "$REVIEW_PLAN_PATH"` → **`charly review --out /tmp/review.txt`**.

The plain form is accepted by **both** the pre-change engine and the embedded-prompt engine, so the invocation is **weld-independent**: safe to land before the org pin moves. Measured against the pinned engine (see How tested). `REVIEW_PROMPT_PATH` is still passed because the charly release in the org pin reads its rulebook from that file; the embedded-prompt engine (welded by `opencharly/charly#626`, **merged**) ignores it, so it is vestigial once the org `CHARLY_VERSION` pin moves and is dropped in the same change that bumps the pin.

### 2. Auto-close after N BLOCKs (configurable, default 5)

A PR that keeps collecting `BLOCK` verdicts — because the author re-pushes without fixing the findings — grows its own comment thread, which drives the reviewer's context into a runaway. The step counts the PR's own `## Review — BLOCK` verdict comments and, at the threshold (`AI_REVIEW_AUTO_CLOSE_AFTER`, default `5`; `0` disables), posts a notice telling the author to open a **NEW** PR with every finding fixed, then closes it. It runs **before** the BLOCK gate.

### 3. Forward the FULL review-knob surface

The review step forwarded only a subset of the knobs the engine reads, so operator variables for them never reached it. This change forwards the remainder as `${{ vars.X || '' }}` (empty = the engine's own default, never a parse of zero). **Reachability depends on the welded engine** — `strings` against the pinned bundle (`v2026.263.2131` → `plugin-review@v2026.263.1956`) classifies each:

| var | what it does | status on the pinned engine |
|---|---|---|
| `AI_REVIEW_TEMPERATURE` | sampling temperature | **ACTIVE** (`strings` hit) |
| `AI_REVIEW_CONTEXT_TOKENS` / `AI_REVIEW_CONTEXT_MARGIN` | the fail-closed context-size guard | **ACTIVE** (hits) |
| `AI_REVIEW_SESSION_ID` | session-affinity header value (empty disables) | **ACTIVE** (hit) |
| `AI_REVIEW_TOP_P` | nucleus sampling | INERT (absent until the pin moves to `v2026.265.0505`) |
| `AI_REVIEW_FREQUENCY_PENALTY` / `AI_REVIEW_PRESENCE_PENALTY` | the measured repetition guard | INERT (absent) |
| `AI_REVIEW_STOP` | comma-separated stop sequences | INERT (absent) |
| `AI_REVIEW_PROMPT_EXTRA` | operator text appended to the embedded rulebook | INERT (absent) |
| `AI_REVIEW_POST_COMMENT` | post the review as ONE PR comment (true/false) | INERT (absent) |

The INERT knobs become ACTIVE when the org `CHARLY_VERSION` pin moves to the release welding `plugin-review@v2026.265.0505` (opencharly/charly#626, **merged**). Forwarding them now is forward-compatible: the engine ignores unknown env. `AI_REVIEW_OUT` is deliberately **not** forwarded — the review step owns that path. A defined-empty var is treated as unset by the engine (`getenvAny` returns `""` and every knob caller guards on non-empty), so `|| ''` means "no override".

### Change 2 — the auto-close branches, and the count fix (the gate's own harness)

```console
$ python3 .github/tests/validator-gate-harness.py
...
scenarios: 17    assertions: 259
ALL PASS: 259 assertions across 17 scenarios, run against the real workflow run: bodies (fakes for charly and gh).
exit=0
```

The harness caught two real defects during development: (a) the auto-close step was first placed **after** `Gate (BLOCK)` (which exits 1), so absent `always()` it would have been skipped forever — it is now before the gate; (b) the auto-close notice rendered the **threshold** as the headline count instead of the actual `$blocks`, so a PR with 8 BLOCKs read "Auto-closed: **5** unanswered BLOCK verdicts" beside "received **8**". The headline now binds `$blocks`, and the new `auto-close-over-threshold-count` scenario (block_count=8) FAILS on the old args and passes on the fix. The harness is wired in via `.github/workflows/validator-harness.yml` on every pull_request.
