# 2026.278.1516 — feat(validator)!: auto-close a PR immediately on ONE INCONCLUSIVE verdict

Closes #166.

## Summary of changes

The auto-close step in `.github/workflows/pr-validator.yml` bounded **both** verdict classes with **one** number: it counted the validator's `BLOCK` and `INCONCLUSIVE` comments together and closed the PR at `AI_REVIEW_AUTO_CLOSE_AFTER` (default 5). An `INCONCLUSIVE` verdict is the provider producing **no answer** — not a code finding — so a PR in that class stayed open across up to five full verdicts (~20 min each, #91) with nothing actionable on the thread, and every run grew the comment thread that drives the reviewer's runaway (`plugin-review#30`). Measured this session: PR 3 in `opencharly/pod-qemu-guest-agent` returned `INCONCLUSIVE` and sat open with nothing to fix on it.

The bound is now **per verdict class**.

- **`INCONCLUSIVE` — bound `1`.** `INCONCLUSIVE_THRESHOLD` is a CONSTANT of the workflow and is deliberately **not** org-configurable: "the provider produced no answer" is a fact about the engine, not a per-repo tuning choice. The FIRST `INCONCLUSIVE` closes the PR. The gate posts this run's own verdict notice **after** the auto-close step, so the step now takes `VERDICT` as an env input and counts this run's `INCONCLUSIVE` **by construction** — which is what makes the first one close rather than the second.
- **`BLOCK` — unchanged**, `vars.AI_REVIEW_AUTO_CLOSE_AFTER || '5'`. A finding IS actionable on the same thread, so a fixing push stays the normal path; the bound still catches an author who re-pushes without fixing.
- **`AI_REVIEW_AUTO_CLOSE_AFTER=0`** (or a non-numeric value) stays the ONE off switch and disables **both** classes — the `INCONCLUSIVE` rule is deliberately not carved out of it.
- **The close notice** now names the per-class bound, both class counts, and the remedy: open a **clean PR from scratch** — a fresh branch and a fresh thread — after **5 BLOCKs** (or `AI_REVIEW_AUTO_CLOSE_AFTER`) **or ONE INCONCLUSIVE**. Never another push, re-run, or re-open on the thread.
- **The gate's `INCONCLUSIVE` remedy strings** stop advising a re-run and name the clean-PR route, and a shared "Thread policy" line is added to the `INCONCLUSIVE` notice.
