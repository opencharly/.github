# 2026.296.1238 — feat(ci): run dotgithub's own jobs on the self-hosted fleet

## Summary

Nine `runs-on: ubuntu-latest` lines in this repository's own workflows become
`runs-on: ${{ vars.CI_RUNNER_LABEL || 'ubuntu-latest' }}`.

That expression is not new: `.github/workflows/tag-on-merge.yml` — the org-wide reusable job
every repo calls after a merge — has used exactly it. The jobs that still asked for a
GitHub-hosted runner were this repository's own wrappers around it.

| File | Job |
|---|---|
| `.github/workflows/tag-on-merge-dispatcher.yml` | the **template** copied into every repo |
| `org-wide-tag-on-merge-dispatcher.yml` | this repo's copy of that template |
| `workflow-checks.yml` | the static policy + Node boundary checks (**fork-PR guarded**, below) |
| `stalled-automerge-detector.yml` | the 30-minute stall scan |
| `bootstrap-repo-main.yml` | new-repo bootstrap |
| `candy-validate.yml` | the reusable candy gate (**fork-PR guarded**, below) |
| `strip-config-version.yml` | the config-version cutover sweep |
| `retire-per-repo-dispatchers.yml`, `retire-per-repo-candy-gates.yml` | the two retirement sweeps |

`pr-validator.yml` is untouched: it already selects `vars.REVIEW_RUNNER_LABEL || 'ubuntu-latest'`
and therefore already runs on the fleet.

## Why the template line is the one that matters

`scripts/reconcile-tag-on-merge-callers.sh` treats `.github/workflows/tag-on-merge-dispatcher.yml`
as canonical and PUTs it, verbatim, into every repository that has a caller. So this one line is
what moves ~440 repos' post-merge `wait-for-merge` job off GitHub-hosted runners — the
distribution is a separate, mechanical step (`reconcile-tag-on-merge-callers.sh --apply`) that
runs after this lands, and a repo that has never had a caller is still not given one.

## Blast radius

- Org variable `CI_RUNNER_LABEL=opencharly` (measured) selects the self-hosted fleet. The
  `|| 'ubuntu-latest'` fallback keeps a clone of this repo usable before that variable exists,
  and keeps forks — which never see the org variable — on hosted runners. **Vendored upstream
  forks therefore stay on GitHub-hosted infrastructure**, which is the intended split.
- These jobs use `actions/github-script` and shell only; none of them needs Docker, so any
  fleet runner can take them regardless of tier.
- **Fork PRs stay on GitHub-hosted** — see Round 1. The fleet never executes untrusted code.

## Round 1 — the fork-PR finding, fixed

The PASS verdict raised one surface the first commit left open, and it is a real one:

> `workflow-checks.yml` is `pull_request`-triggered, so if org `vars` are visible to fork-PR runs,
> untrusted fork code would execute on the self-hosted fleet instead of ephemeral hosted runners.

Correct. The fleet's runners are **long-lived guests that keep state between jobs** — exactly
what an ephemeral hosted runner is not. A fork PR is untrusted code by definition, so the split
has to apply to it too, not only to vendored forks running their own copy. The two PR-reachable
files now read:

```yaml
runs-on: ${{ (github.event.pull_request.head.repo.fork == true) && 'ubuntu-latest' || (vars.CI_RUNNER_LABEL || 'ubuntu-latest') }}
```

- `github.event.pull_request` is absent on `push` and `workflow_dispatch`, so the first term is
  `false` there and those runs keep taking the fleet.
- `candy-validate.yml` gets the same guard: it is `workflow_call` and is invoked from callers'
  PR workflows, so its runner selection sees the caller's event.

The other seven files are not `pull_request`-triggered (`workflow_dispatch`, `workflow_run`,
`push`, `schedule`) and keep the plain expression.
