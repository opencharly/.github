# 2026.296.0808 — fix(ci): run the review command, give git its safe.directory, and fail red when no verdict comes back

## Summary

`crabbox#16`'s first run of the advisory review went **GREEN having reviewed nothing**. The check is
supposed to be a reviewer; a green that reviewed nothing is worse than a red. Three causes, all in the
container invocation, plus the reason it stayed green:

1. **The image has no ENTRYPOINT.** `Config.Cmd` is `/bin/bash`, so `docker run <image>` opened an
   interactive shell that exited 0 immediately and printed nothing — the verdict file came back empty.
   The command is now named explicitly (`… "${IMAGE}" clawsweeper-review`), which is how the image's own
   R10 bed invokes it.
2. **git refused the mounted tree** as `dubious ownership` — measured with a live container. The
   container now sets `safe.directory=/target`.
3. **The engine writes its review state under `<target>/.git/clawsweeper/`**, so a READ-ONLY mount died
   on `mkdir '/target/.git/clawsweeper/reviews'` — measured. The mount is writable now. The tree it
   points at is a THROWAWAY fetch made in this job (`refs/pull/<n>/head` into `${RUNNER_TEMP}`), never
   the runner's own checkout, so a write there reaches nothing that can be pushed. The isolation that
   matters is unchanged: no GitHub token enters the container and no Docker socket is mounted, and the
   verdict still leaves on stdout for this workflow to post.
4. **The check could not go red.** A non-zero exit only warned. Now a non-zero exit, an EMPTY verdict, or
   `status: failed` all fail the run — while the comment step still executes and carries the redacted
   reason.

The isolation wording is corrected EVERYWHERE, including the `NETWORK` paragraph that still claimed a
"writable view of the PR" was absent:

```
# NETWORK. `--network bridge` gives the container EGRESS, which it needs: the model endpoint
# is remote. What it does NOT have is a credential, a socket, or any writable path that can be
# pushed: the writable tree it sees is the job's own throwaway fetch (see above), and the
# runner's checkout is never mounted here at all.
```

## The two facts the diff could not show

Both live in code this PR does not touch, so here they are from the file at this head.

**`/target` is a job-local fetch, not the runner's checkout** (the fetch step):

```bash
review="${RUNNER_TEMP}/review"
rm -rf "$review" && mkdir -p "$review"
git init -q "$review"
git -C "$review" -c "http.extraheader=AUTHORIZATION: basic ${auth}" \
  fetch -q --no-tags "${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}" \
  "+refs/pull/${PR_NUMBER}/head:refs/remotes/pr/head" \
  "+refs/heads/${base_ref}:refs/remotes/origin/${base_ref}"
git -C "$review" checkout -q -B pr refs/remotes/pr/head
```

`actions/checkout` is never used, and `${REVIEW_DIR}` is that directory: a fresh, private fetch under
`${RUNNER_TEMP}`, discarded with the runner's temp dir.

**The comment still runs when the review step fails** (the comment step):

```yaml
- name: Post the review comment, updating the previous one
  # ONLY when the review step actually ran. A pin or fetch failure is an INFRA error and
  # must not be dressed up as "the engine produced no verdict".
  if: always() && steps.review.outcome != 'skipped'
```

`outcome` is `failure` for a red review step, so the comment step executes and carries the redacted
reason; only a NEVER-RUN review (`skipped`) suppresses it.

the model boundary and wrote a report, which is the whole assertion. With the org key present on the
runner, the same path produces a real verdict.)
