## Summary

**Pin the lint toolchain in the validator instead of resolving `go-version: 'stable'`.**

RCA 2026-10-09 (`opencharly/pod-github-runner#9`), measured end to end:

- `actions/setup-go@v5` with `go-version: 'stable'` resolves **from the network** to the newest released Go, which became **1.27.2** on the self-hosted runner;
- the lint step installs the pinned **golangci-lint v2.13.2**, a **prebuilt release built with go1.27.0**;
- Go 1.27.2's **export-data version (5)** is newer than that linter can read (**maximum 4**), so it fails with

  ```
  could not load export data: internal error in importing "encoding"
  (export data version 5 is greater than maximum supported version 4) (typecheck)
  ```

- the failure is on **every module root**, so the step fails for **every repo the org lints on that runner** — and because it fails, **steps 15–16 (`Head check-runs`, `Enable auto-merge`) are skipped**, so even a `## Review — PASS` verdict cannot arm auto-merge.

## Why a pin, and not the eviction that was tried first

**Eviction was attempted on the runner and did not fix it.** The cached `_work/_tool/go/1.27.2` was removed from the three affected instances (`no-4`, `no-6`, `no-8`), all eight instances then read only `1.26.4 1.27.1`, and **the very next job re-downloaded 1.27.2** (`no-2` now carries it) and **failed again at the same step**. Measured:

```
evicted:   no-4, no-6, no-8 -> 1.26.4 1.27.1        (verified across all 8 instances)
next run:  reached an instance, re-resolved 'stable' -> 1.27.2 re-downloaded
result:    completed/failure   failed=[golangci-lint (the repo's declared lint, enforced)]
```

That is the evidence that a **pin** — or raising the `GOLANGCI_LINT_VERSION` **org variable** to a linter built with a Go >= the runner's toolchain — is the only permanent lever. *This PR is the pin; the variable remains the operator's cheaper alternative, and either one fixes it.*

**`1.26.4`, chosen because it is readable by the pinned linter BY CONSTRUCTION**: a toolchain can always read its own build's export data, and the pinned linter's own build (`go1.27.0`) writes at most version 4 — so any toolchain at or below that is readable. *Whether `1.27.1` also writes 4 was NOT measured and is not claimed; round 1 withdrew that claim and round 2 replaced the version rather than argue for it.* `1.26.4` is also already present in every runner's tool cache, so the pin costs no download.

## Review round 1 correction — the 1.27.1 claim is WITHDRAWN as unproven

The reviewer is right, and the objection is sharper than the fix's author realised: **the two halves of my stated mechanism do not sit together.**

- Measured (in the runner's own log, from failing `spec`/`sdk` jobs): the pinned linter reports `export data version 5 is greater than maximum supported version 4`, i.e. it can read **at most 4**.
- Measured: `'stable'` resolved to **1.27.2**, the cached toolchain the failing jobs used.
- **NOT measured — and this is the hole: that `1.27.1` avoids the failure.** If the export-data format bumped 4 -> 5 anywhere inside 1.27.x, then 1.27.1 writes 5 too and **this pin fixes nothing.**

**And the pin has not even been exercised on this head**: with the review verdict `BLOCK`, the workflow skips steps 12-14, so `setup-go` and `golangci-lint` never ran here. *My earlier reading — "the lint did not fail, so the pin worked" — was wrong: the lint did not run at all.*

**So this PR now claims only what is measured:**
1. `'stable'` resolves from the network to the newest Go and landed on **1.27.2** on the self-hosted runner;
2. the pinned prebuilt linter cannot read what that toolchain writes (**version 5 > maximum 4**), and the step then fails on **every** module root — org-wide, for every repo linted there;
3. therefore the step fails, steps 15-16 (`Head check-runs`, `Enable auto-merge`) are skipped, and **even a `## Review — PASS` verdict cannot arm auto-merge**;
4. eviction does not fix it: the cached `1.27.2` was removed from `no-4`/`no-6`/`no-8`, the next job re-downloaded it (`no-2` now carries it) and the step failed again.

**The measurement that decides the pin's value, named for whoever finishes this** (cheap, one runner):
```
# on a runner instance, with the cached toolchains and the pinned linter:
for v in 1.26.4 1.27.1 1.27.2; do
  echo "== $v"; "$HOME/actions-runner/_work/_tool/go/$v/x64/bin/go" version
  # does the PINNED linter read what THIS toolchain writes?
done
# and, decisively, run the linter the CI runs against a module built by each:
```
*If `1.27.1` is readable and `1.27.2` is not, the pin is the fix as written. If **both** are unreadable, the pin must go lower (or the other lever — the `GOLANGCI_LINT_VERSION` org variable, a linter built with a Go >= the runner's toolchain — is the only fix).*

**The one-action alternative remains available and is cheaper than this PR:** raising the org variable `GOLANGCI_LINT_VERSION` needs no repo change at all.
