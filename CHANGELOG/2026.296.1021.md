# 2026.296.1021 — feat(ci): make the required validator independent, and arm auto-merge only when everything is green

## Summary

`validate / validate` is the org's ONE required context, so anything it waits on, or fails on, blocks
every PR in the org. It was doing both.

**What was measured.** On `crabbox#17`, twelve CI jobs were in flight on a six-runner pool. Gate B — which
lives inside the required check — waited its bounded 600 s and then turned `validate / validate` **red**
with

```
could not confirm this head is green: still in flight after 600s — Apple VM, Connector Lifecycles, …,
Go core, Go modules, Native Windows contracts, Scripts, Worker
```

while the review verdict on that head was **PASS**. A failing repo job reddened the same check the same
way. The gate was coupled to CI it does not own.

**The split — three jobs, and the lint moves OFF the critical path.**

| Job | Is | Does |
|---|---|---|
| `validate` | the **required** context | the review verdict, and nothing else. No checkout, no lint, no check-run reads, no arming. It cannot wait on another job and cannot be reddened by one. |
| `lint` | not required, **parallel** | gate A: the repo's declared golangci-lint over the PR head. Nothing in it depends on the verdict, so the merge gate's path becomes `max(review, lint)` instead of `review + lint`. |
| `arm` | not required | `needs: [validate, lint]`; runs when the verdict is PASS **and** lint passed, then gate B (every check run on the head) and only then arms native squash auto-merge. |

**The invariant is preserved and strengthened.** Nothing merges on a head whose checks are not all green —
`charly#791` (merged while `go` was still running, and `go` then failed) and `charly#795` (merged on an
already-red head) stay closed. It is now enforced by *what gets armed* rather than by reddening the
required check, which is where the coupling came from.

Because the required context is now evidence like any other, gate B **includes `validate / validate`
itself** — and drops the `details_url`/run-id discriminator it used before: both jobs share one workflow
run id, so that discriminator would have excluded the required check too and quietly weakened the gate to
"everything except the check that matters most". It excludes exactly one thing now, its own
`validate / arm`.

The arm job's wait budget rises to **3600 s**: a timeout there means "not armed yet", never "the required
check is red".

## A BLOCK or INCONCLUSIVE still fails loud and hard

The verdict gates did **not** move: `BLOCK` exits 1, an unparsable/ambiguous verdict exits 2, and
`INCONCLUSIVE` exits 3 — each with an `::error::`, each failing **`validate`**, which is the org's
required context. So the check goes RED, the comment explains why, and branch protection blocks the merge.

Because `arm` is `needs: validate` and gated on a PASS verdict, it does not even start on any of those:
nothing is armed and nothing is softened. That invariant is now written at the gates themselves, so a
future edit cannot quietly move them into the non-required job.

| Verdict | `validate` (required) | `arm` | Merge |
|---|---|---|---|
| PASS | green | waits for every check, then arms | on green |
| BLOCK | **red, exit 1** | skipped | blocked |
| INCONCLUSIVE | **red, exit 3** | skipped | blocked |
| ambiguous parse | **red, exit 2** | skipped | blocked |

## How tested

The workflow is its own test: this PR runs the modified file (a `pull_request` uses the head's workflows)
against its own CI.

What the run must show, and what to look for in the checks:

1. **`validate / validate` green, on evidence** — the review verdict alone, while the repo's CI jobs are
   still queued/running. Before this change an in-flight `Scripts` at the wrong moment could redden it;
   now it cannot see `Scripts` at all.
2. **`validate / arm` waiting, then arming** — it appears after `validate` completes, polls until every
   check settles (including `validate / validate`), and only then arms squash auto-merge.
3. **The failure path** — if any CI job fails, `arm` goes red and does **not** arm; `validate / validate`
   is untouched.

Nothing about the verdict, the comment, the auto-close counter or the evidence bundle moves: those all
stay in `validate`, which is why the evidence steps stayed with it while the three merge-gating steps
moved.

## Rulebook compliance

| Rule | How it is honoured |
|---|---|
| R1 | The failure was measured (`still in flight after 600s` on a real PR) and the cause named: the required check read checks it does not own. |
| R2 | One gate per property: the verdict is the verdict, the arming is the arming; no second copy of either. |
| R3 | No retry and no suppression: an unconfirmable head still means "not armed", it just no longer means "the required check is red". |
| R5 | The old in-check gate B is deleted, not left beside the new job. |

## Change classification

Org gate change (`pr-validator.yml`): a second, non-required job. The required context keeps its name and
its meaning for the review verdict; what changes is that it no longer depends on any other job.
