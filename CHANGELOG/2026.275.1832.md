# 2026.275.1832 — fix(gate): record the runner and the review step's outcome in the abort evidence (#158)

## Summary

`charly/pr-validator` can complete **FAILURE without ever producing a review**: the required `validate / validate` check goes red, no verdict comment is posted, and the PR is blocked with nothing actionable. Measured on opencharly/opencharly#333 head `b77cca4` (run `36966957868`, attempts 1–3 — the third finally posted the gate's own `## validator INCONCLUSIVE` class comment at 05:36Z):

| attempts | runner | `review_rc` | `review.log` |
|---|---|---|---|
| 1–2 | `charly-githubrunner-no-4` | *(empty)* | **absent** |
| 3 | `charly-githubrunner-no-4` | **137** (SIGKILL) | **2 lines** |
| comparison head `7c93b9e6` | `charly-githubrunner-no-1` | 0 | 1917 lines |
| comparison head `75344e58` | `charly-githubrunner-no-1` | 0 | 1330 lines |

Attempt 3's two-line log names the chain:

```
WARNING: charly is a dev/worktree build (not installed at /usr/bin or /usr/local/bin); NOT loading the installed package's plugins from /usr/lib/charly/plugins …
Downloading github.com/opencharly/plugin-review:main...
```

The workflow sets `CHARLY_PLUGIN_DIR=$D/plugins` (line 252) after extracting the pinned `charly-plugins-linux-amd64.tar.gz` into `$D/plugins` — yet the engine still went to the **network** for `plugin-review:main`, i.e. it did not find `plugin-review` among the plugins it was told to load, and that runtime download was then killed (137). The engine never reached the PR's diff.

**The gap this PR closes is the diagnosis cost.** `gh run view` / `gh run rerun` 404 on this ruleset workflow, so the evidence artifact is the only machine-readable output left — and while it does record what the review produced (`review_rc`, the log), it does **not** record **where it ran**. Establishing the runner identity cost a separate `gh api .../jobs` call, and on attempts 1–2 that endpoint returned an empty step list. Two fields now answer it, and the run summary shows them:

```yaml
          RUNNER_NAME: ${{ runner.name }}
          REVIEW_OUTCOME: ${{ steps.review.outcome }}
```

```diff
+            echo "runner_name=${RUNNER_NAME:-<unset>}"
+            echo "step_outcome_review=${REVIEW_OUTCOME:-<unset>}"
```

plus two rows in the step summary. Purely additive to the reporting path: the step keeps `if: always()` + `continue-on-error: true`, so a reporting failure still cannot turn a PASS run red, and **no verdict logic is touched**.

**Deliberately not included:** the natural third field, `steps.ensure-charly.outcome`, cannot be referenced at all today — the offline gate rejects it (see *How tested*). Renaming that id fails the harness's own id contract, so the honest fix is the harness's expression evaluator, a self-modifying-security surface needing its own validation. Filed with its exact repro as **#159** rather than bolted onto this change (R4).

Relates to **#158** (the filed defect, whose RCA this PR's artifact-reading advanced) and **#159** (the evaluator gap found while fixing it).

## Fix for the review verdict (B18 / R1)

The verdict on `4ba3295` raised one finding, and it was correct: the added summary row for the review step's outcome used **unescaped backticks** inside a double-quoted `echo`, so the label was command-substituted (the shell ran `Run the review engine`, printing `command not found` into the evidence step's own log) and the row rendered unlabeled. The sibling value cell and every neighbouring row were escaped correctly; that line now matches them.

```diff
-              echo "| step `Run the review engine` | \`${REVIEW_OUTCOME:-n/a}\` |"
+              echo "| step \`Run the review engine\` | \`${REVIEW_OUTCOME:-n/a}\` |"
```
