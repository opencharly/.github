# 2026.295.1252 — docs: exclusion from the org ruleset is not a ban on landing

## Summary

The org-level README said forks "carry no required check and their same-repo PRs merge without an org verdict", and that a repo in the excluded set "must first become non-fork / active / main-default" to be tagged/validated. Read with the `discover_excludes` filter, that invited the conclusion that a forked repo in this org is a defect that cannot land.

It is not. Exclusion is about the ORG-WIDE AUTOMATIC coverage only. The live org shows three different landing paths among excluded forks, and the excluded set is not one category:

- `crabbox` is a fork and carries a repo-scoped ruleset requiring the SAME `org-wide-pr-validator-required.yml`;
- `gst-wayland-display` is a fork on a non-`main` default (`stable`) and carries its own rules there, including `validate / validate`, plus three CalVer tags minted out-of-band;
- `openclaw-enterprise` is a fork with zero branch rules, so no branch check is enforced; its PRs run its own `.github/workflows/ci.yml` and merge on that CI signal. PR #2 merged 2026-10-13.

The fix states what an exclusion means (no org-wide required check, no automatically minted CalVer tag) and what it does not (a prohibition). It splits the excluded set into four categories and says ONLY the fork category is a landing target: a vendored upstream, an artifact-branch sink, and an archived read-only repo are not. Every real rule is kept: a NEW repo is still created non-fork so it inherits the org gate. README-only — no gate, ruleset or template file changes.
