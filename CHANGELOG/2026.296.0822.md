# 2026.296.0822 — fix(ci): let Codex's bubblewrap sandbox start inside the container

## Summary

`crabbox#16`'s second run of the advisory review **worked end to end** — it fetched the real PR, ran the
engine, produced a full report about `opencharly/crabbox` at `3cd68f0d` — and then failed at the model
boundary because Codex's own sandbox could not start inside the container:

```
bwrap: No permissions to create new namespace, likely because the kernel does not allow
non-privileged user namespaces. See <https://deb.li/bubblewrap>
```

The container now runs with `--security-opt seccomp=unconfined --security-opt apparmor=unconfined`.

## The flags are MEASURED, and each removes a distinct block

Round 1 of this PR proposed both flags on reasoning alone, and the validator was right to reject that: an
unbounded LSM relaxation must be justified by what it actually buys. A disposable probe
(`.github/workflows/clawsweeper-probe.yml` on branch `probe/claw-userns`, never merged) ran the same
image, the same fixture and a deliberately INVALID key against the real runner in four variants:

| `--security-opt` | result on the runner |
|---|---|
| none | `bwrap: No permissions to create new namespace` — userns creation blocked |
| `seccomp=unconfined` | userns now works, and the NEXT block appears: `bwrap: Failed to make / slave: Permission denied` (mount propagation) |
| `apparmor=unconfined` | userns still blocked — AppArmor is not what stops it |
| `seccomp=unconfined apparmor=unconfined` | **Codex runs**; the only failure left is the deliberately invalid key |

Run: <https://github.com/opencharly/.github/actions/runs/39923920820>

So the two relaxations are not a blanket sweep: seccomp is what permits the unprivileged user namespace
bubblewrap needs, and AppArmor is what permits the mount operation bubblewrap performs inside it. Each
is load-bearing, and neither is sufficient alone.

**The narrower options that were considered and why they were rejected:** dropping either flag is
disproved by the table above; `--privileged` grants capabilities, devices and host mounts far beyond this
and is strictly broader; and Docker has no "extend the default profile" mechanism, so a custom seccomp
file would mean vendoring the entire default profile to change one entry — the same relaxation, harder to
review.

## What this does and does not widen — and the runtime identity

- **Runtime UID:** the image declares `USER 1000` (`ubuntu`); the container never runs as root.
- **No token reaches the container.** The full invocation, from this file:

  ```bash
  docker run --rm \
    --network bridge \
    --security-opt seccomp=unconfined \
    --security-opt apparmor=unconfined \
    -e OLLAMA_API_KEY \
    -e CLAWSWEEPER_TARGET_REPO="${GITHUB_REPOSITORY}" \
    -e BASE_SHA="${BASE_SHA}" \
    -e TARGET_DIR=/target \
    -e GIT_CONFIG_COUNT=1 \
    -e GIT_CONFIG_KEY_0=safe.directory \
    -e GIT_CONFIG_VALUE_0=/target \
    -v "${REVIEW_DIR}:/target" \
    "${IMAGE}" clawsweeper-review
  ```

  No `-e GITHUB_TOKEN`, no `--env-file`, no `-v /var/run/docker.sock`, no `--privileged`, no added
  capability. The only secret in the container is the model key the review needs.
- **What IS relaxed is kernel attack surface** — that is stated plainly rather than hidden behind the
  reach argument. It is accepted here because the alternative is no review at all: without it, Codex's
  sandbox cannot start, and the previous round established that a check which cannot review must be RED,
  not silently green.
- **Reach:** `/target` is the job's own throwaway fetch under `${RUNNER_TEMP}`, never the runner's
  checkout (`actions/checkout` is not used anywhere in this workflow), and it is discarded with the
  runner's temp dir.
