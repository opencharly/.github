## Summary

The review engine's **measured root cause** is an unbounded reasoning generation,
not the workflow's timeout. This PR aligns the workflow with the engine fix and
stops hardcoding a generation bound.

**Two symptoms, one cause** (measured against the real validator context — 28 KB
rulebook + 79 KB PR thread + 120 KB diff):

- 13m49s runs: `turn request attempt N/3 failed: LLM request exceeded the 5m0s whole-request deadline`;
- empty reviews: `turn 2: final content len=0` (`verdict_lines=0`).

The engine sent **no `reasoning_effort` and no `max_tokens`**, and
`deepseek-v4.1-flash` is a reasoning model: the unbounded request generated
**1.75 MB of reasoning over 786 s** before answering.

**Why it is now fixed end-to-end.** The engine half (bounding the generation, plus
the `max_tokens` reasoning-budget relationship) landed in
`opencharly/plugin-review#10`; the charly release `v2026.263.0616` welds it, and
the org pin `vars.CHARLY_VERSION` is set to that release. So the six knobs this
workflow passes are ACTIVE, and the gate returns verdicts in tens of seconds. This
workflow PR only passes the engine's own bounds through and removes the hardcoded
cap.

**Ownership split:** the ENGINE owns the generation bound
(`opencharly/plugin-review#10`). This workflow passes the engine's bounds through
and no longer hardcodes a deadline.

### The zero-length handling — source excerpt, not assumption

`|| ''` produces a **defined, empty** env var. The pinned engine treats that as
UNSET: its `getenvAny` returns `""` for any env whose value is `""`, and every
knob caller guards with `if v := getenvAny(…) != ""`:

```go
// parse.go
func getenvAny(names ...string) string {
	for _, n := range names {
		if v, ok := os.LookupEnv(n); ok && v != "" {
			return v
		}
	}
	return ""
}

// review.go — every AI_REVIEW_* knob uses this guard
if v := getenvAny("AI_REVIEW_ATTEMPT_TIMEOUT"); v != "" {
	if n, e := parseInt(v); e == nil && n > 0 {
		cfg.AttemptTimeout = time.Duration(n) * time.Second
	}
}
```

A defined-empty `AI_REVIEW_ATTEMPT_TIMEOUT` therefore skips the branch and leaves
`cfg.AttemptTimeout` at zero; the engine then applies its own **per-turn**
default (15 m) plus a 3 m idle bound. It is NOT parsed as `0`.

**The per-turn cap is NOT bounded by the job wall clock.** The 15 m applies to ONE
turn, inside a loop of up to `AI_REVIEW_MAX_TURNS` (unchanged here: default 20), so
`timeout-minutes: 20` can be reached across several turns with no single turn
exceeding 15 m — which is exactly what the live cancellations showed (runs killed
at `20:00` with `Terminate orphan process: pid … (plugin-review)`). The bounds
that actually keep a run short are the per-turn idle-silence bound and the
engine's bounded generation; the wall clock is the last-resort backstop.
