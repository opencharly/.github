# 2026.293.1928 — ci(pr-validator): pin the toolchain the declared-lint gate runs under (#219)

## Summary

Pins `GOTOOLCHAIN` on the declared-lint step of `pr-validator.yml`. One env key plus its rationale — the whole diff.

**The defect (`opencharly/.github#219`).** Unpinned, the lint run inherits whatever toolchain the runner image provides, so **the gate's verdict changes with the runner**:

```console
# clean detached worktree at unmodified origin/main - no PR, no change of mine
$ GOTOOLCHAIN=go1.27.1 golangci-lint run ./...
0 issues.

$ GOTOOLCHAIN=go1.27.2 golangci-lint run ./...
4 issues: * typecheck: 4
```

**The mechanism, from the linter's own message** (quoted as prose because the full line is long and a fence may not abbreviate):

> `cmd/charly-lib-gen/main.go:20:2: could not import flag (... could not import encoding (-: could not load export data: internal error in importing "encoding" (cannot decode "encoding", **export data version 5 is greater than maximum supported version 4**); please report an issue)) (typecheck)`

That is a **Go toolchain / linter ABI mismatch**: the `go1.27.2` toolchain writes export data **version 5**, and this `golangci-lint` binary decodes a maximum of **version 4**. It is not a finding about any code — it is the linter being unable to *read* the standard library at all.

These land in `cmd/charly-lib-gen/main.go`, which no PR in this programme touches, and **the same failures reproduce on `main` with no PR at all** — so no PR can fix them from inside its own tree.

**How it showed up.** On `opencharly/sdk#432` two jobs linted the same head and disagreed:

| job | resolved toolchain | result |
|---|---|---|
| `go` (own CI lint) | `go1.27.1` | **success**, 12 s |
| `validate` (step 15, this gate) | `go1.27.2` | **failure** |

Two jobs, two toolchains, two answers. The review verdict on that PR was **PASS** and every other check green, and auto-merge could not arm.

**The workflow already knew.** Its own comments record the sensitivity and leave the failing case unanswered:

```
$ GOTOOLCHAIN=go1.26.4 golangci-lint run ./...   -> rc=0  "0 issues."
$ GOTOOLCHAIN=go1.27.1 golangci-lint run ./...   -> rc=0  "0 issues."
$ GOTOOLCHAIN=go1.27.2 golangci-lint run ./...   -> (unanswered — and it is 4 issues)
```

This pins the missing answer, using the same org-variable pattern the step already uses for `GOLANGCI_LINT_VERSION`.

## How tested

The workflow parses, and the key is asserted on the step that carries the id rather than eyeballed:

```console
$ python3 -c "import yaml; d=yaml.safe_load(open('.github/workflows/pr-validator.yml')); s=[x for j in d['jobs'].values() for x in j.get('steps',[]) if x.get('id')=='golint'][0]; print(s['env']['GOTOOLCHAIN'])"
${{ vars.GOLANGCI_LINT_GOTOOLCHAIN || 'go1.27.1' }}
```

The **choice of default** is measured, not assumed — `go1.27.1` is the toolchain at which the tree that fails under `go1.27.2` reports `0 issues`. The failure and the clean case were both reproduced locally on `origin/main`.
