# 2026.293.1955 — ci(pr-validator): make the declared-lint findings survivable and reachable (#219)

## Summary

Makes the declared-lint gate's findings **survive the job and be reachable**, which is what `.github#219` is about. One step's `run:` block changes; nothing else in the workflow moves.

**The defect, stated exactly — including a correction of my own framing.** I originally described this as "the findings are unreadable". They were not unreadable; they were **unreachable**:

- `golangci-lint` wrote them to stdout, which lives in the step log — and `gh run view --log-failed` returns **empty** for these runs, so from a normal host the findings could not be retrieved at all;
- the failure message said *"fix the findings above"* while pointing at nothing an author could open;
- the review engine's reasoning does land in the `validator-evidence` artifact, but the lint's own output does not.

So the fix is not "print the findings" — they were printed. It is **put them somewhere durable and name it in the message**.

**The change:**

- both lint invocations write through `tee` into a findings file;
- on failure that file is appended to `$GITHUB_STEP_SUMMARY`, which renders on the run page and is fetchable through the API;
- the `::error::` message now says the findings are in this run's **step summary and job log**, instead of "above".

## Why the guard is shaped that way

Two platform facts decide it, and neither is visible in the diff:

- a pipeline reports the status of its **last** command, so `… | tee` alone would leave this gate green while the linter failed;
- this step declares no `shell:` and the job sets no `defaults.run`, so it inherits GitHub's `bash --noprofile --norc -eo pipefail`. With `pipefail` the pipeline returns the linter's status, and with `-e` an unguarded failure exits the shell **at the pipeline** — before `fail=1`, before the summary write, before the `::error::`, which would hide the findings exactly when they matter.

The code therefore puts the pipeline in an `if` condition, which the shell exempts from errexit, so `pipefail` gives the condition the linter's status and the shell survives to record it:

```bash
if ! ( cd "$root" && GOWORK=off "$BIN" run ./... ) 2>&1 | tee -a "$FINDINGS"; then
  fail=1
fi
```
