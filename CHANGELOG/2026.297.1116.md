# 2026.297.1116 — fix(ci): an unread head must never arm auto-merge, and a SLOW sibling is not a FAILED one

## Summary

The `Head check-runs` step of the reusable `charly/pr-validator` workflow — the merge guardrail that arms native auto-merge — had three defects. All three are fixed here, and each fix is measured against the pre-#229 text.

**1 — an unreadable head was reported as GREEN, and auto-merge was armed on it.** The snapshot read `curl … | jq …`, and in a pipeline the exit status is jq's: a failed API read produced an empty body, jq reads a blank line as NO INPUT, so it printed nothing and exited 0. The snapshot was therefore EMPTY rather than missing, every count read from it was the empty string, the comparisons failed with `[: : integer expected`, every `if` that read them was false, and the classification fell through to its last line. Measured on the pre-#229 text (the paste is in `## How tested` below): an unreadable head ended with `all  check run(s) on this head passed — safe to arm auto-merge` — the count empty, because the snapshot carried no checks at all — and exit 0. The next step, "Enable auto-merge", therefore ran on a head whose checks this gate had never read, and the step's own guard ("refusing to arm auto-merge on an unread head") was unreachable. The fetch is now checked rather than assumed, an empty body is an unread head rather than an empty check set, and an unread head is its own class that refuses to arm. The jq filter itself is unchanged, byte for byte.

**2 — "a check did not pass" and "a check is still RUNNING" shared one exit code and one remedy.** Both were exit 1, and the remedy for a still-running check named a re-run of the whole validator — a FRESH REVIEW, which can even change the verdict (opencharly/.github#186). Measured on the pre-#229 text: a sibling still running when the budget ended produced "could not confirm this head is green: still in flight after 3600s" and exit 1 — indistinguishable, in the run's conclusion and in the required check's colour, from a check that had genuinely failed. The two are separate classes now, and the exit code IS the class:

| exit | class | what it means | remedy |
|---|---|---|---|
| 0 | GREEN | every check on the head passed | arm it |
| 1 | NOT-PASSED | a check on the head did not pass — a FINDING about the change | fix it and push |
| 2 | IN-FLIGHT | a check is still RUNNING — not a finding | re-run this job only |
| 3 | UNREAD | the head could not be read | refuse to arm |

The in-flight class names its cheap remedy, and the remedy is real: GitHub's REST docs re-run "a job and its dependent jobs" — downstream, never upstream — and `arm` is terminal, so re-running it does not re-run the review and the verdict cannot change. The old remedy spent a fresh review to learn that the check was still running.

**3 — the wait's budget was a second, unrelated number.** It was an independent literal (3600 s) under the step's own backstop (4200 s), and nothing asserted how the two related. The shape that #236 replaced made the gap observable: a 600 s literal against an 840 s backstop, which truncated a real ten-minute sibling and exited 1 (opencharly/marketplace#540, 2026-10-23). The budget is now derived from the step's own backstop (`backstop - margin`), so the wait can never outlast the step that waits and the two can never drift apart again; the new test asserts the relation (`timeout-minutes × 60 == SETTLE_BACKSTOP_SECONDS`).

Measured, so the numbers are not guesses: the slowest check the arm job actually waits for took 1073 s over one sample set and 974 s over another — 262 sibling samples in all, drawn from 415 completed check-runs across the org's recent PRs. The derived budget (4200 − 300 = 3900 s) exceeds every one of them. No measured sibling has yet exceeded the 3600 s literal the base carries today, so what that budget still carried was the unasserted relation rather than an observed truncation — while the two defects above are reachable on every PR, not only on a slow one.

- `scripts/head-settle_test.sh` (new) — the coverage. The settle logic lives inside the reusable workflow and runs in the CALLER's repository, so it cannot be a script here: the test EXTRACTS the shipped step's `run:` text and runs THAT text against fixtures, so the two cannot drift.
