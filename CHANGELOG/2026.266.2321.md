# 2026.266.2321 — fix(tag-on-merge): tag root-module proxy-consumed repos in Go form

## Summary

Fix the org-wide tag-on-merge reusable so repos that are **root Go modules consumed via the module proxy** get the Go-module tag form `v0.<YYYYDDD>.<HHMM>`, not the plain repo CalVer. Adds `plugin-gh` to that set and guards the subdir-module branch against it.

**The bug (a repeat of the spec rot).** The reusable hardcoded `const goModuleRepos = ['sdk', 'spec']` to decide the tag shape. A consumer's `go.mod` pins these repos at `v0.<YYYYDDD>.<HHMM>` exactly; a plain `v<YYYY>.<DDD>.<HHMM>` tag (major ≥ 2, which would require a `/vN` module-path suffix) is **unusable as a module version**. `spec` was once missing from that list and its Go-module releases stopped advancing while its repo tags kept going — every spec change after that merged but unconsumable. `plugin-gh` is the same shape and was never in the list.

**Why it matters now.** `plugin-gh` had **no tag-on-merge dispatcher at all** (only `ci.yml`), so its merged `document` op landed untagged. The companion PR (opencharly/plugin-gh#5, installs the dispatcher) will start tagging every merge, and without this fix the tag it mints would be the wrong shape.

**The change.**
- `goModuleRepos` gains `'plugin-gh'`, with a comment making the criterion explicit ("root module with an external Go-module consumer", not merely "has a root go.mod") and an instruction to add new such repos.
- The subdir-module branch keys on the `plugin-` **name prefix**; that is true for `plugin-gh` but its module is at the ROOT, so an unguarded rule would mint a bogus `candy/plugin-gh/v0.<…>` tag resolving to nothing. Guarded with `!isGoModuleRepo`. Every genuine subdir-module plugin repo has no root go.mod, so their tags are unchanged.

`charly-streamer` (also a root module, but a binary nobody imports via the proxy) is deliberately NOT added, and the comment states why.
