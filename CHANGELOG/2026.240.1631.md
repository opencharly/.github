# 2026.240.1631 — fix(tag-on-merge): tag spec in Go-module form, like sdk

## Summary

`spec` is a **root Go module**. `charly/go.mod` requires it as

```
github.com/opencharly/spec v0.2026232.520
```

— the same `v0.<YYYYDDD>.<HHMM>` shape as `sdk`. But the tagger special-cased only `sdk`:

```js
const tag = repo.repo === 'sdk'
  ? `v0.${y}${doy}.${parseInt(hh + mm)}`
  : `v${y}.${doy}.${hh}${mm}`;
```

so `spec` received the plain repo CalVer (`v2026.240.1623`), which is not a usable module version.

## Why this is worth fixing now

The effect is silent and total. spec's Go-module releases stopped at **`v0.2026232.520`** (day 232)
while its repo tags kept advancing to day 240:

```
$ git ls-remote --tags .../spec | … | grep '^v0\.' | tail -1
v0.2026232.520

$ git ls-remote --tags .../spec | … | tail -1
v2026.240.1623
```

Every spec change merged in between is **unconsumable** — not blocked, not delayed, but *unnameable*
by any consumer, because no version exists that contains it. Nothing fails; the change simply never
reaches anyone.

Three merged spec PRs are in that state right now (`opencharly/spec#57`, `#58`, `#59` — the
`#Box.init` enum and batch B2's service-schema fields), and their consumer legs in `plugin-init` and
`charly` cannot proceed until a `v0.*` tag exists.

## The change

Replaces the single-repo equality with an explicit list of the root Go-module repos:

```js
const goModuleRepos = ['sdk', 'spec'];
const tag = goModuleRepos.includes(repo.repo) ? … : …;
```

**Candy repos are unaffected** — they are already tagged separately, in `candy/<repo>/v0.…` form, by
the module-tag branch further down.

## How tested

The workflow is `actions/github-script` inline JS, so the branch was exercised in isolation with the
same inputs the workflow computes:

```
$ node -e '<the branch, verbatim>'
sdk          v0.2026240.1645
spec         v0.2026240.1645
charly       v2026.240.1645
plugin-wl    v2026.240.1645
```

sdk's behaviour is unchanged; spec joins it; every other repo keeps the plain CalVer.

```
$ python3 -c "import yaml; yaml.safe_load(open('.github/workflows/tag-on-merge.yml'))"
YAML parses
```

## Backfill

Tag creation is unchanged and remains **idempotent** (`getRef` → create-if-missing), so
re-processing an already-tagged PR is a no-op. Once this lands, re-running `tag-on-merge` against
spec's recent merges mints the missing `v0.*` tags with no special handling — the tag is derived from
each PR's own merge-commit time, so backfilled tags carry their true timestamps rather than today's.

## Rulebook compliance

- **R1** — root-caused before remediation: the missing tags were traced to this branch by reading
  the shared workflow, not inferred from the symptom. The first suspicion — that spec's own
  `tag-on-merge.yml` differed from sdk's — was checked and disproved; the two are byte-identical and
  both delegate here.
- **R2** — fixed at the cause. Cutting a one-off `v0.*` tag by hand would have unblocked my three
  spec PRs while leaving every future spec change in the same state.
- **R3** — one list, one decision site; sdk is not special-cased twice.
- **R4** — no workaround: no hand-cut tag, no pseudo-version pin in the consumers.
- **R5** — N/A — nothing removed.
- **R6** — `git status` checked; branch off fresh `main`; no force-push, no bypass.
- **R7** — behaviour proven by executing the branch, not by reading it.
- **R8/R9/R10** — N/A — a CI workflow with no build artifact, binary or disposable bed. Its real
  gate is the next spec merge producing a `v0.*` tag, which I will verify after this lands.

## Change classification

- **Class:** CI/workflow change — release tagging.
- **Verification gate:** branch executed in isolation + YAML parse.
- **Attribution tier:** `analysed on a live system` — the defect and the fix were both established

## Risk

Low and one-directional: the only behaviour change is which tag string `spec` gets. A wrong tag is
additive (an extra ref), and creation is idempotent, so a re-run cannot clobber an existing tag.
